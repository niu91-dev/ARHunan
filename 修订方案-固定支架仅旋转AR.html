固定支架 · 仅旋转 · 安卓 Pad
重新梳理的 AR 方案

约束大幅收窄后，问题从「六自由度定位」降为「两自由度角度测量」——复杂度下降约一个数量级

结论速览：Pad 位置固定、只能旋转，意味着不需要 SLAM、不需要解算位置、不需要重定位、不需要标记位姿真值。唯一未知量是 yaw 和 pitch 两个角度。位置直接写死成标定常量，旋转用传感器测。

推荐落地顺序：① 先用 Pad 自带姿态传感器跑通（零成本、当天可验证）→ ② 若漂移不可接受，在支架旋转轴上加两个磁编码器走 USB HID（几十元、精度提升一个数量级）→ ③ 若还需要绝对参考，再叠加标记校正。

一、约束变化带来的简化

维度上一版假设（手持自由移动）本版实际（固定支架 + 仅旋转）简化效果
自由度 6 DOF（位置 + 姿态） 2 DOF（yaw + pitch） 求解量减到 1/3
位置来源 每帧解算，会漂移 安装时量一次，写进常量 彻底消除位置漂移
标记的用途 解算完整位姿（需要精确的 markers.json） 最多只做角度校正，甚至完全不用 不需要测标记位姿
旋转范围 任意 ±18° / ±12°（小范围） 漂移累积可控
重定位 丢失后需要重新锁定 位置永远已知，不存在丢失问题 去掉整个状态机
遮挡 需要配准后做深度遮挡 位置固定 → 遮挡关系可预计算 可选，非必需
唯一需要新增的物理前提：Pad 装在支架上的姿态（安装倾角、横竖屏）必须固定不动。安装后调好就不再变——这个安装姿态会被一次性标定吸收进常量里。

这个推算给出了清晰的选型标尺——贴合误差 5 px 以内需要 0.25° 的角度精度：

测量方式典型精度折算屏幕误差是否达标
12 位磁编码器（AS5600）0.09°1.7 px优秀
视觉标记 PnP0.15°3.0 px优秀
设备陀螺仪（短时）0.20°3.9 px达标
精密电位器0.30°5.9 px临界
设备加速度计（pitch 绝对）0.50°9.8 px勉强
USB HID 手柄电位器0.50°9.8 px勉强
磁力计定北（室内）2.00°39.4 px不可用
关键结论：磁力计在室内展馆不可靠（钢结构、电机、灯光镇流器都会干扰），39 px 的误差肉眼非常明显。不要指望「设备绝对朝向」能直接用来定 yaw。

三、旋转测量的三个实现

S1

Pad 自带姿态传感器 先做这个 零成本

做法：用浏览器 deviceorientation 事件读设备姿态。安卓 Chrome 无需权限弹窗（iOS 才需要 requestPermission()）。

可用部分：beta（俯仰）来自加速度计测重力方向，是绝对值且稳定，直接可用于 pitch。

问题部分：alpha（偏航）在室内磁环境下不可靠；若退回纯陀螺积分则会缓慢漂移。

应对：① 用「零点复位」按钮让用户手动归中；② 只在单次会话内使用，每次开机重新归零；③ 若展馆磁环境干净（无大型钢构/电机），实测后可能直接可用。

工期：1–2 天可跑通并实测漂移量。建议作为第一步验证手段——先量出真实漂移，再决定要不要上硬件。

S2

支架旋转轴编码器 最稳 需少量硬件

推荐实现：USB HID 手柄方案。支架的两个旋转轴各装一个 AS5600 磁编码器（12 位，0.09°）或精密电位器，接到一块 RP2040 / Pro Micro，枚举成一个双轴 USB 游戏手柄，通过 OTG 接安卓 Pad，浏览器直接用 Gamepad API 读取。

为什么选 USB HID 而不是蓝牙：免配对、免电池、免驱动、延迟低、插上就能用。展项现场最怕的就是"蓝牙连不上"。

精度：AS5600 → 1.7 px；电位器 → 5.9 px。建议直接上磁编码器，差价很小。

优势：零漂移、零延迟、不受光照/遮挡/磁干扰影响，是固定展项里最省心的方案。装上之后基本不需要维护。

工期：硬件 3–5 天（含支架改造）+ 软件 1 天。

S3

标记辅助校正 可选增强

做法：沙盘边框贴 1–2 个 AprilTag，摄像头低频（如 2 Hz）检测一次，解算出的角度用来校正 S1/S2 的漂移。

因为位置已知，这里不需要完整的 PnP——只需从一个标记的图像位置反推偏航/俯仰，未知量只有 2 个，非常鲁棒。

用途：如果走 S1（陀螺仪）路线且实测漂移明显，加这个就能获得绝对参考；如果走 S2（编码器）路线，完全不需要。

工期：3–4 天（标记检测 WASM 集成 + 角度解算）。

选型决策

先做 S1→ 实测漂移→ 漂移 < 0.3°/分钟？→ 是：就用 S1，收工
否→ 上 S2 编码器→ （S3 一般可跳过）
我的建议：直接按 S2 编码器设计，但用 S1 做过渡。理由：支架既然是为这个展项定制的，加装编码器的边际成本很低，而它能一次性消除漂移、光照、遮挡、磁干扰四类问题——这些都是展项长期运行中最容易翻车的点。S1 则用来在硬件到货前先跑通整条软件链路。

四、"假 AR" 的四个档位

你说「甚至可以是假 AR」——这里给出从真到假的四档，每档都写清代价。建议做到档位 B，有余力再上 A。

档位做法需要的校准效果代价
A · 真透传 摄像头画面做背景 + 全息内容贴合实体沙盘 FOV 校准 + 位置校准 + 高精度旋转（≤0.25°） 最像真 AR，山体后的点被正确遮挡 高需标定相机内参
B · 半透传 推荐 摄像头画面做背景，内容按大尺度贴合（容忍 1–3° 误差） FOV 粗调 + 位置校准 + 中精度旋转 观感接近 A，误差在可接受范围 中FOV 用滑杆现场对位即可
C · 纯虚拟 不做摄像头透传，直接显示虚拟沙盘，视角随旋转联动 只需旋转测量，FOV 可以随便定 用户看到"会转的三维沙盘"，但知道那是屏幕内容 低无需内参标定
D · 屏幕锁定 不测旋转，内容固定屏幕位置 无 旋转 Pad 时内容不跟随，AR 感完全消失 最低但不推荐
为什么 D 档不推荐：±18° 旋转会让内容相对实体沙盘滑动近 28% 屏幕宽度。这个量级肉眼极其明显，用户会立刻感觉"内容浮在屏幕上，没有贴在沙盘上"，反而比不做 AR 更差。
档位 B 的 FOV 怎么定（不用内参标定）：做一个「对位校准」模式——屏幕上叠加虚拟沙盘的四角轮廓，操作员拖动 FOV 滑杆，直到轮廓与透过摄像头看到的实体沙盘边缘重合。存进配置，一次搞定。这是展项行业最常用的做法，比实验室标定更实用。

五、一次性安装校准

安装时做一次，之后写入配置文件。这是整个方案里唯一需要人工介入的环节。

#校准项做法产物
1支架位置 实测支架相对沙盘中心的：安装高度、离中心距离、沿边左右偏移 { height, distance, lateral }
2零点姿态 把 Pad 转到名义视角（正对沙盘中心），记录此刻的传感器读数作为零点 { zeroYaw, zeroPitch }
3轴向与符号 左右各转一次、上下各转一次，确认传感器轴与相机轴的对应关系和正负方向 { axisMap, signYaw, signPitch }
4屏幕方向补偿 Pad 是横屏还是竖屏、屏幕旋转 0/90/180/270°，需在角度映射里补偿 { screenOrientation }
5FOV 对位（仅档位 A/B） 叠加虚拟沙盘轮廓，调 FOV 直到与实体沙盘边缘重合 { fov }
6旋转限位 实测支架机械限位角度，替换 Demo 里的 ±18°/±12° { yawLimit, pitchLimit }
容易漏掉的一项：屏幕方向补偿。安卓 Pad 横屏时，设备坐标系会整体旋转 90°。如果不补偿，用户左右转 Pad 会变成画面上下动。这是这类项目最常见的翻车点之一，务必在步骤 3/4 里显式验证。

六、稳定性处理

因为位置固定，稳定性问题只剩「旋转输出要不要滤波」这一件事。

问题处理参数建议
传感器噪声抖动 One Euro 滤波（角度是标量，比四元数简单得多） minCutoff ≈ 1.0 Hz、beta ≈ 0.01
静止时亚像素抖动 角度死区：变化小于阈值时冻结输出 < 0.05° 时不动（约 1 px）
缓慢漂移（仅 S1 路线） ① 零点复位按钮；② 开机自动归零；③ 标记低频校正（S3） 复位按钮放在不显眼处，操作员可用
传感器断连（USB 被拔） 冻结最后角度 + 状态角标提示；恢复后平滑过渡 过渡 0.3 s，避免瞬移
好消息：因为位置永远固定且已知，上一版方案里的整套「丢失恢复状态机」（正常/降级/短时丢失/持续丢失/重定位）可以全部删掉。只剩一个「角度输入异常」的简单兜底。

相机设置建议

  • 镜头缩放必须固定。Demo 里的 1–3.5× 数字变焦会破坏 FOV 一致性，走档位 A/B 时必须锁定为 1×，或直接移除该控件。
  • 摄像头分辨率固定。让 getUserMedia 请求固定的 1280×720，并在校准时用同一分辨率，避免浏览器自适应切换导致 FOV 跳变。
  • 后置摄像头。Demo 已用 facingMode: 'environment'，保持即可。

八、实施步骤与验收

建议顺序（约 2–3 周可到档位 B）

  1. 第 1 步（1 天）· 锁定常量。实测支架的 height / distance / lateral，写死进配置，先把三个滑杆废掉——这一步不依赖任何传感器，立刻能验证"固定位置"是否正确。
  2. 第 2 步（2 天）· S1 跑通。接 deviceorientation，做零点校准和轴向映射，观察旋转是否跟随。同步实测漂移量。
  3. 第 3 步（1 天）· 判定。若漂移 < 0.3°/分钟 → 直接用 S1。否则下单编码器。
  4. 第 4 步（1 天）· 档位 C 验证。先做纯虚拟版本，确认旋转联动流畅、UI 稳定。这一步就能回答"假 AR 够不够用"。
  5. 第 5 步（2 天）· 上透传。接回摄像头，做 FOV 对位校准，进入档位 B。
  6. 第 6 步（3–5 天，可选）· S2 编码器。硬件到货后替换角度来源。因为接口统一，软件侧只换一个模块。
  7. 第 7 步（1 天）· 档位 A。若追求极致，加深度遮挡与更严的 FOV 标定。

验收标准

指标档位 C 目标档位 B 目标档位 A 目标
旋转跟随延迟≤ 60 ms≤ 60 ms≤ 40 ms
静止抖动≤ 2 px≤ 2 px≤ 1 px
内容与实体沙盘贴合误差不要求≤ 30 px≤ 5 px
漂移（连续 30 分钟）≤ 5°≤ 1°≤ 0.3°
帧率≥ 30 fps（目标 60）

必测场景

  1. 横竖屏验证：左右转 Pad，画面必须是水平方向动，不能上下动。
  2. 回到零点：转到底再转回正对沙盘，内容应回到原位（验证无漂移累积）。
  3. 连续运行 30 分钟：记录角度漂移量，这是决定 S1 还是 S2 的关键数据。
  4. 快速来回转：不应有滞后拖影或过冲振荡。
  5. 慢速微调：小幅度转动时不应有"卡顿跳格"（死区设置过大导致）。
  6. USB 插拔（S2）：拔掉再插上，应能自动恢复且无角度跳变。
  7. 光照变化：开灯/关灯，走 S1/S2 时不应受影响（这正是它们优于视觉方案的地方）。
最省事的一条路：如果第 4 步的档位 C 已经让用户满意（旋转联动顺滑、UI 稳定），并且展项方接受"屏幕上是虚拟沙盘"这个设定，那么可以完全不做透传、不做内参标定、不做标记——整个项目就是"加一个角度传感器 + 换掉三个常量"。这也是最不容易在长期运行中出问题的形态。
本方案基于 hunan-terrain-ar-demo 实测参数（4.8×5.5 m 台面 · 16× 垂直夸张 · Three.js r180 · 原支架范围 ±18°/±12°）与「安卓 Pad + 固定支架 + 仅旋转」的实际约束推导。
精度数字按 65° 水平视场 / 1280 px 采集宽度估算，实际需在目标设备上实测后修正。生成日期 2026-09-29。
