# 设备能力自检页 · 局域网部署说明

在**小米平板6**上打开自检页，实测姿态传感器漂移率、ARCore/WebXR、摄像头、外设，据此决定 AR 方案走哪条路。

---

## 一、为什么必须用 HTTPS

`http://192.168.x.x` **不是安全上下文（secure context）**。Chrome 在非安全上下文下会**静默屏蔽**：

| 能力 | 依赖接口 | HTTP 下表现 |
|---|---|---|
| 姿态传感器 | `DeviceOrientationEvent` / `DeviceMotionEvent` | 事件不触发，页面无任何报错 |
| 摄像头 | `getUserMedia` | `navigator.mediaDevices` 为 `undefined` |
| WebXR / ARCore | `navigator.xr` | 不可用 |

自签名 HTTPS（点一次「继续前往」）**即为安全上下文**，以上全部可用。
这就是本目录用 `serve-lan.py` 起 HTTPS 而不是 `python -m http.server` 的原因。

## 二、启动（推荐：双击）

直接双击 **`start-lan.bat`**，窗口会打印：

```
  平板访问 : https://192.168.31.180:8443/
  本机自测 : https://127.0.0.1:8443/
```

同时生成 **`qr-access.png`**（访问二维码）并在窗口内打印 ASCII 二维码。

> 窗口**不要关**，关掉即服务停止。

### 命令行方式

```bash
python serve-lan.py --port 8443
python serve-lan.py --port 8444          # 端口被占用时换一个
python serve-lan.py ./public --ip 192.168.31.180
```

脚本只用 Python 标准库（`qrcode` 可选，缺失时自动降级为纯文本 URL）。

## 三、平板端操作

### ⚠️ 必须用 Chrome，不要用小米自带浏览器

**实测结论**：小米平板6 自带的 **MIUI 浏览器** 在 60 秒内只推送了 **5 个**姿态事件
（正常应 30~60 Hz，即 ~3600 个），且 ALPHA 全程恒定不变 → **传感器数据不可用**。

MIUI 浏览器的 UA 里带着 `Chrome/135.0.7049.79`，**那只是它用的内核版本号，不代表具备
Chrome 的设备能力**。它的 WebXR（`navigator.xr`）也不存在。

页面现在会自动识别并提示这一点，报告里也会写明 `浏览器` 与 `浏览器是否适合本测试`。

**推荐顺序：Chrome > Edge > 其他 Chromium 内核浏览器。**
国产浏览器（小米 / 华为 / OPPO / vivo / 夸克 / UC / QQ / 搜狗 / 百度）的设备能力常被裁剪，
不要用。

### 操作步骤

1. 平板连上**与电脑同一个 Wi-Fi**（`192.168.31.x` 网段，小米路由器）。
2. 用 **Chrome** 扫码，或手输 `https://192.168.31.180:8443/`。
3. 出现「您的连接不是私密连接」→ 点 **高级** → **继续前往 192.168.31.180（不安全）**。
   - 这是自签名证书的正常提示，只此一次；之后即为完整安全上下文。
4. **先看第 2 节的「事件频率（实时）」**：
   - 显示 **30~60 Hz** → 正常，可以继续
   - 显示 **个位数 Hz 或「无事件」** → 浏览器没在推传感器数据，**换浏览器，别往下测了**
5. **做第 3 节「旋转响应检查」**（这是判断传感器是否可用的前提，见下节说明）：
   点按钮后**缓慢左右转动平板约 45°，持续 5 秒**。
6. **做第 5 节的「实际创建 AR 会话」**（如果 `ARCore 声称支持` 是 true）：
   点按钮会真的请求一次 `immersive-ar` 会话。**成功的话整件事就简单了**——
   ARCore 直接给 6DoF 位姿，不需要陀螺仪积分、不需要 AprilTag、不需要编码器。
7. 旋转检查通过后，再做 **第 4 节「漂移测试」**：把平板**静置 60 秒不要动**，
   **页面保持在前台、屏幕不要熄灭**（进后台浏览器会停发事件，测试作废）。
8. 测试结束后点 **「导出报告」**，把结果发回来。

### ⚠️ 记得关掉 Chrome 的「桌面版网站」

平板在 Chrome 里开了「桌面版网站」后，UA 会变成 `X11; Linux x86_64`，
看起来像台 Linux 电脑。**传感器、ARCore 其实都还在**，但会导致两个问题：

- 页面会把设备误判成「非移动设备」（现在会靠触屏能力兜住，但报告里会出现
  `疑似桌面版网站模式: true`）
- **视口尺寸和像素比会变**（例如 `1152x720 @2.5x` 而不是 `1280x800 @2.25x`），
  直接影响后续 AR 叠加的对位计算

**Chrome 菜单 → 取消勾选「桌面版网站」→ 刷新页面。**

### 为什么会有「ALPHA 全程不动」的红色提示？

漂移测试结束后如果看到 **`ALPHA：60 秒内全程不变，这一路不可用`**，**先别急着换设备**——这有两种完全相反的成因，页面自己分不清：

| 成因 | 含义 | 怎么判断 |
|---|---|---|
| ① 传感器确实很好 | 静止时真的零漂移 | 旋转检查里 **ALPHA 有响应** |
| ② 系统把陀螺仪置于低功耗模式 | 静止时角速度**直接报 0**，一转起来才输出 | 旋转检查里 **ALPHA 有响应**（转的时候） |
| ③ 该浏览器没提供真实偏航数据 | 转也不动 | 旋转检查里 **ALPHA 无响应** |

**所以顺序很重要：先做旋转响应检查，再跑漂移测试。**

页面现在同时测量**两路偏航来源**，并自动选用可用的那一路：

- **① `deviceorientation.alpha`** —— 浏览器融合后的偏航
- **② `devicemotion.rotationRate.alpha` 积分** —— **原始陀螺仪角速度**，绕过浏览器融合，最可信

如果 ALPHA 冻结但陀螺仪有响应，页面会提示「**改用陀螺仪积分做偏航**」，
并直接给出陀螺仪积分算出的漂移率。第 2 节新增的「偏航来源逐路排查」表可以实时看到三条通道各自是否活跃。

> **注意静止时的低功耗门控**：实测平板静止时 `deviceorientation` 只以约 **7 Hz** 推送，
> 而转动时会升到 **100 Hz 以上**，`devicemotion` 则恒定 **60 Hz**。
> 所以**做 AR 叠加要用陀螺仪那一路（60 Hz）**，ALPHA 在静止时会有明显卡顿。

> **参考量级**：典型 MEMS 陀螺仪零偏约 0.01~0.1 °/s，积分后对应 **0.6~6 °/min** 的漂移。
> 所以实测落在方案 B / C 区间是正常的，方案 A（< 0.3 °/min）需要很好的器件或频繁重标定。

### 结果可信度（页面会自动判定）

| 标记 | 含义 | 处理 |
|---|---|---|
| `测试期间页面进过后台` | 事件被浏览器暂停 | 保持前台重测 |
| `事件频率过低` | < 5 Hz，基本没在推数据 | 换 Chrome 重测 |
| `ALPHA 冻结，待旋转响应检查定性` | 见上一节，**不一定是坏事** | 先做旋转检查 |
| `漂移结果可疑` | 最大偏移 > 5°，中途被碰过 | 重测 |

### 重点看三个数

- **Yaw 漂移率（°/min）** —— 决定是否需要 AprilTag 兜底
  - `< 0.3 °/min` → **方案 A**：纯传感器 + One Euro Filter，每分钟重标定一次
  - `0.3 ~ 2 °/min` → **方案 B**：加 One Euro Filter 并把重标定周期压到 2~3 分钟；或贴 AprilTag 做周期性校正
  - `> 2 °/min` → **方案 C**：放弃纯陀螺仪偏航，改用 AprilTag 视觉定位，或加装 USB HID 编码器直读角度
- **陀螺仪积分漂移率（°/min）** —— 比 ALPHA 更可信的那一路
- **旋转检查里 ALPHA / 陀螺仪是否有响应** —— 判断传感器到底活不活

> 阈值依据：65° HFOV / 1280 px ⇒ **1° ≈ 19.7 px**。要把贴合误差压在 5 px 内，需要 **0.25°**
> 的角分辨率。所以 0.3 °/min 的含义是「一分钟内累计漂移仍在 0.3° 量级」——超出就得靠滤波或重标定兜。

## 四、AR 跟踪稳定性测试（`ar.html`）

**自检页回答「ARCore 能不能用」，这个页面回答「好不好用」。**

前置条件：自检页第 5 节显示 **`AR会话实测成功: true`**。

### 它测什么

平板装在**固定支架**上时，**相机位置本应恒定**。所以页面直接统计
**相机位置波动**——这就是 ARCore 的跟踪误差，是个客观指标，不靠肉眼判断。

页面上会实时显示：

| 指标 | 含义 |
|---|---|
| **跟踪状态** | 由真实位姿数据驱动：`跟踪中` / `跟踪不稳 N%` / `无位姿 Ns` |
| **相机位置波动** | 三个轴波动量的合成，**越小越好**（< 10 mm 极好，> 80 mm 会看到明显抖动） |
| 位置漂移（起→今） | 起点与当前位置的距离 |
| 各轴波动 X / Y / Z | 定位问题出在哪个轴 |
| 跟踪丢失帧占比 | 丢失率越高说明特征越少、越难跟 |
| 位姿采样 / 平面检测 / 渲染帧率 | 判断跟踪与渲染是否真的在跑 |
| 朝向 yaw / pitch | 实时姿态 |

### 操作

1. 打开 `https://192.168.31.180:8443/ar.html`（自检页顶部也有入口链接）
2. **先点「先测相机」** —— 确认相机硬件、权限、页面出图都正常，看到实时画面后关掉预览
3. 点 **「进入 AR」**，允许相机权限
4. **把平板装到现场那个固定支架上，对着沙盘**
5. 一进去，**正前方偏下**应该出现一块青色网格地板 + 绿色圆环 + 4 根橙色小柱子。
   这四样东西是**世界锚定**的：跟踪准，它们就像钉在真实空间里；跟踪漂移，会看到它们相对沙盘滑动
6. **缓慢左右旋转平板**，幅度尽量大，来回 3~4 次
7. 屏幕任意处**点击可放置锚点**（绿环），锚点也钉在真实空间里，肉眼即可看出稳不稳
8. 点「结束并出报告」，导出 JSON。报告页有**「再次进入 AR」**按钮，不用刷新页面

### ⚠️ 实测结论：本机 ARCore 不建立跟踪（2026-09-29）

小米平板6 上的实测数据：

| 指标 | 读数 | 含义 |
|---|---|---|
| 累计渲染帧 | 1074（45 秒）| 渲染循环正常 |
| 位姿采样 | **0** | `getViewerPose()` 每帧都返回 null |
| 跟踪丢失帧 | **1074（100.0%）** | 一帧都没拿到位姿 |
| 平面检测 | **无平面** | 命中测试什么也没找到 |
| 「先测相机」 | **画面正常** | 相机硬件、权限、页面渲染链路都没问题 |

**结论：ARCore 的会话能创建，但 ARCore 自己从未建立跟踪。** 相机是好的（`getUserMedia` 已验证），
是 ARCore 拿不到相机 / 建不起跟踪。

`getViewerPose()` 返回 null 是**跟踪未建立**的标准信号（规范规定位姿无法确定时返回 null），
配合「命中测试无平面」，指向 ARCore 运行时本身。

**要做的确认**（按顺序）：

1. 跑 `ar-min.html`（**AR 最小可复现测试**）—— 把 WebXR 用法剥到只剩一个立方体，
   不调命中测试、不申请额外特性。若它也是 0 位姿，**页面代码就被完全排除**。
2. 平板「设置 → 应用 → 应用管理」里搜 **Google Play Services for AR**（包名 `com.google.ar.core`）：
   - 没有这个应用 → 就是根因，国行机型常见
   - 有但版本很旧 → 尝试更新（需要 Google Play 环境）
   - 有且是最新 → 检查它是否被授予**相机权限**
3. 装任意一个 ARCore 应用（如 Google「Measure」）测试：若它也黑屏，就是设备级问题。

### ⚠️ 进去之后整屏全黑怎么办

**先分清是「只有截图黑」还是「眼睛看到也黑」。**

AR 的相机画面在 Android 上走的是**系统硬件合成层**（和相机 App 的预览同一类通道），
而 HUD 走的是普通 UI 层。**很多机型截图只能拍到 UI 层，拍不到相机层** ——
所以截图里 HUD 正常、下面全黑，**未必**说明眼睛看到的也是黑的。

按这个顺序确认：

| 现象 | 说明 |
|---|---|
| 眼睛能看到沙盘画面，只是截图黑 | **正常**，截图限制而已，继续测 |
| 眼睛看不到网格/圆环/柱子，但看得到沙盘 | WebGL 层没渲染 → 把结论发回来 |
| 眼睛看到全黑，且 HUD 里「跟踪状态」一直显示 `无位姿` | 相机 / ARCore 没出图，看下一行 |
| 「先测相机」也打不开或也是黑的 | 相机硬件或权限问题，**不是 AR 的问题** |

页面已做的针对性处理：

- AR 期间把 `html/body` 底色设为 `transparent`，排除「不透明底色盖住相机层」
- `renderer.setClearColor(0x000000, 0)`，清屏全透明
- 舞台放到「正前方 1.4 m、眼下方 0.6 m」，一进去就必定在视野里
- HUD 里直接显示 `位姿采样` / `跟踪丢失帧` / `平面检测` / `渲染帧率`，
  连续 5 秒拿不到位姿会弹出红色告警 —— **即使全黑也能判断跟踪有没有在跑**

### 判定与后续

- **波动 < 30 mm** → ARCore 可以直接用，走真实 WebXR AR 路线
- **波动 30~80 mm** → 可用，但叠加会有轻微抖动，建议加滤波
- **波动 > 80 mm** → 通常是因为**只旋转、没有位移**，相机缺少视差，ARCore 难以约束深度。
  这时在沙盘边框贴 **AprilTag / 已知标记**做一次配准，把误差拉回来

> 页面里渲染的网格、坐标轴、标杆都是**世界锚定**的。跟踪准的时候，它们就像钉在真实空间里；
> 跟踪漂移时，会看到它们相对沙盘滑动——这是最直观的观察方式。

## 五、退路：相机 + 陀螺仪叠加（`ar-camera.html`）

**如果 `ar.html` 里 ARCore 的相机透视在这台机器上出不来，这条路线是兜底方案。**

它**完全不用 ARCore**：

| 能力 | 来源 | 可靠性 |
|---|---|---|
| 相机透视 | 普通 `getUserMedia` + `<video>` | **100% 可靠**（就是相机 App 那条链路） |
| 旋转（yaw / pitch / roll） | `deviceorientation` 陀螺仪 | 已实测 60 Hz、漂移 0.078 °/min |
| 平移（前后左右上下） | ❌ 没有 | 需要 AprilTag / 已知标记补 |

### 操作

1. 打开 `https://<ip>:8443/ar-camera.html`（`ar.html` 入口页底部也有链接）
2. 点 **「启动相机与传感器」**，允许相机权限
3. 屏幕上应同时看到**真实相机画面** + 青色网格 / 绿色地平线 / 橙色沙盘占位体
4. **缓慢左右旋转**平板 —— 虚拟网格会跟着转，但相对真实场景**不该滑动**
5. 用 **「视场角」滑块**（默认 65°）把虚拟地平线调到和真实地平线重合，
   再用 **「水平校准」**微调俯仰。这两个值会记进报告
6. 点 **「结束并出报告」** 导出 JSON

### 判定

- **alpha 漂移 < 0.3 °/min** → 3DoF 叠加路线可行
- **alpha 波动范围 < 0.05°** → 静止时被低功耗门控了（正常），需重测并确认转动时 alpha 会变
- **没有收到任何陀螺仪数据** → 这条路走不通，换浏览器或换设备

### 适用边界

- 展项允许平板**装在固定支架上「只转不移」** → 这条路完全够用
- 要支持**自由移动** → 需要 AprilTag / 已知标记做绝对定位（这也是 `ar.html` 结果不理想时的下一步）

## 六、Demo：湖南地形 AR 沙盘（`ar-gyro-demo.html`）

**这是「陀螺仪方案」的完整形态** —— 把真实湖南 DEM 地形叠加在真实相机画面上，全程不用 ARCore。

### 它包含什么

| 部分 | 来源 |
|---|---|
| 地形 | 真实湖南 DEM，256×292 网格（约 2.4 km/格），`assets/terrain-height.f32` |
| 配色 | 真实配色贴图，**带湖南轮廓 alpha**，地形自动裁成湖南形状（`assets/terrain-color.png`）|
| 地点 | 11 个地点 + 完整展项文案（`sites.js`，经纬度 → 墨卡托 UV → 地形表面）|

### 这是横屏展项，不是手机应用

**设计形态就是横屏**，原因不是审美，是几何：横屏才能拿到平板后摄**完整的水平视场**，
虚拟地形的左右边缘才可能和真实沙盘的左右边缘对上。竖屏下水平视场被裁掉一大半，
怎么调都对不齐。

界面为此做了三件事：

| 处理 | 做法 |
|---|---|
| 竖屏拦截 | `@media (orientation: portrait){ body.ar-active #rotate{display:flex} }` —— 纯 CSS，弹出「请把平板横过来」 |
| UI 重排 | 顶部状态条 **6 格横铺**；地点信息卡移到**右侧竖栏**；设置面板移到**左侧竖栏**；底部操作条一行放下 7 个按钮 |
| 全屏 + 锁横屏 | 底部 **「全屏」** 按钮：`requestFullscreen()` 后尝试 `screen.orientation.lock('landscape')` |

> `screen.orientation.lock()` 在桌面浏览器会直接抛异常，代码里是 try/catch 容错的。
> 真机 Chrome 上（全屏状态下）通常可以锁定成功；锁不上也不影响使用，横过来即可。

**视场角语义在横屏下是「水平视场角」**（`P.hFov`，默认 65°），垂直视场由宽高比推出来：

```js
const h = THREE.MathUtils.degToRad(P.hFov);
const v = 2 * Math.atan(Math.tan(h / 2) / cam3.aspect);
cam3.fov = THREE.MathUtils.radToDeg(v);
```

### 取景几何：一个我算错过的坑

**默认取景不是拍脑袋定的，但第一版确实算错了。** 记录在这里，因为它非常容易重犯。

```
❌ 错误算法（我第一版就是这么写的）：
   相机到沙盘中心距离 = √(1.50² + 1.30²) ≈ 1.98 m
   1.80 m 宽沙盘的张角 = 2·atan(0.9 / 1.98) ≈ 48.8°
   → 结论「落在 65° 里，还有余量」
```

**这个算法在俯视下完全失效。** 近端角点 `(0.9, 0, +D/2)` 离相机比中心近得多，
它的真实张角是 **水平 34.5°、垂直 30.8°**，而半视场只有 **32.5° / 21.7°** ——
真机一跑，地形直接撑出画面下沿和右侧。这就是你截图里看到的现象。

正确做法是**把四个角点变换到相机空间逐个判角**：

```
相机在 (0, h, d) 看向原点：
  f = (0, -h, -d)/L         光轴
  u = (0,  d, -h)/L         相机 up
  depth = (P - eye)·f
  水平角 = atan(|Δx| / depth)
  垂直角 = atan(((P - eye)·u) / depth)
判定用归一化比值：> 1 即出画
```

实测数据（`tableW=1.8`、`hFov=65`、16:10 横屏）：

| 相机位 | 水平比 | 垂直比 | 结果 |
|---|---|---|---|
| 高 1.50 / 距 1.30（旧默认） | 1.079 | **1.698** | ❌ 上下超出 70% |
| 高 1.15 / 距 2.35（新默认） | 0.836 | 0.765 | ✅ 四角入画 |

> **为什么必须站这么远？** 平板后摄水平视场约 65°，在 2 m 见方的沙盘前，
> 物理上就装不下整个沙盘 —— **真实相机也拍不全**。
> 所以「地形超出画面」其实是「虚拟和真实一致」的表现，不是 bug。
> 想看得更全，只能站远、抬高、或换广角镜头。

node tools/framing-params.mjs --tableW 2.8 --circle --dist 2.0 --height 0.56 --solve

**扫描结果**（直径 2.80 m，相机距中心 2.00 m，高度 0.56 m）：

| 水平比值 | **1.391** | 左右出画 39% |
| 垂直比值 | **1.301** | 上下出画 30% |

`--solve`：要保持俯角 15.64° 全部入画，需 `camDist ≥ 2.56 m / camHeight = 0.72 m`

> 页面 `cornerFractions()` 按**四角**算，而圆形沙盘没有角。页面会显示矩形边界的

> 离线脚本 `--circle` 按圆周 72 点采样，结果更准确。
> 离线脚本 `--circle` 按**圆周 72 点**采样，报「出画 6.39 倍」。
> 两者都不算错，只是**对「沙盘形状」的假设不同**。要让页面也按圆算，需给
> `cornerFractions()` 加圆形采样分支。

### AR 标注锚定与视野裁剪（核心机制）

展项要的效果是：**相机照到沙盘的哪一部分，就只显示那一部分的 AR 标注**；
而且标注必须**相对沙盘绝对静止**（位置和沙盘实体绑定，不跟着相机走）。
比如沙盘最左和最右各有一个标点，转向左只显示左边的，转向右只显示右边的。

拆成三个**互相独立、可分别验证**的机制：

#### ① 锚定：坐标只由经纬度决定

`anchors[]` 里每个标点的世界坐标由 `uvToWorld(geoUv(lon, lat))` 算出，
`buildSites()` 建好之后**再没有任何代码写它**。相机不参与。

> Sprite 标签会朝向相机转 —— 那是**朝向**，不是**位置**。
> 需求要求绑定的是空间位置，所以标签保持 billboard（否则侧看就变成一条线，读不了）。

测试：把相机转到 8 组方位（含 180° 背对），要求每个锚点世界坐标**逐分量不变**。
实测最大漂移 `0.00e+0 m`。

#### ② 映射：相机视野 ↔ 沙盘区域

`visibleGroundPolygon()` 拿一个足够大的地面四边形，
用相机视锥的 **4 个侧面**去裁它，得到「此刻照到地面上的那块区域」；
再裁到沙盘圆周内，画成半透明高亮（顶栏显示覆盖率）。

> ❌ **不要用「远平面 4 个角与地面求交」。**
> 相机接近水平时，画面上半部分的视锥棱是**朝上**的，永远不与地面相交。
> 那种写法一旦遇到朝上的棱就判「没有视野」—— 而实际视野是延伸到地平线的。
> 第一版就是这么写的，结果 `coverage` 恒为 0，还以为是矩阵没更新。
> ✅ 裁半空间没有这个毛病：顶面不与地面相交时，它自然不产生任何裁剪。

实测（相机高 0.56 m、距中心 2.00 m、水平视场 65°、16:10 横屏）：

| 相机朝向 | 覆盖率 | 视野多边形 |
|---|---|---|
| 看向沙盘中心 | **88.6%** | 26 顶点，全部在半径 1.40 m 内 |
| 左 / 右转 20° | 70.3% | 29 顶点 |
| 左 / 右转 45° | 32.0% | 21 顶点 |
| 左 / 右转 60° | 12.8% | 16 顶点 |
| 左 / 右转 90°、背对 | 0% | 空 |

未覆盖的 11.4%（正对时）是**近端一条月牙 + 左右两片弓形**（视锥侧面切掉的部分）。
这个数可以手算校验：近端月牙 0.080 m²、左右弓形各 0.307 m²，合计 0.693 m²，
沙盘圆面积 6.158 m² → 覆盖率 88.7%，与程序输出一致。

> ⚠️ **覆盖率对垂直视场角敏感，而垂直视场角由宽高比推出来。**
> 两个脚本如果没固定视口（`Emulation.setDeviceMetricsOverride`），
> 同一朝向会算出不同覆盖率（实测差 1.2%），看起来像「算法不稳定」，
> 其实只是 `--window-size` 给出的实际视口不是精确的 1152×720。
> 所有 AR 相关脚本都固定了视口。
>
> 另外查越界要用 `node tools/ar-region-check.mjs <URL>`（跑 9 个朝向）。
> 实测 `maxR = 1.403`（R = 1.40，多出的 0.003 是圆裁剪用 48 条切线逼近的弦高），
> **所有朝向、所有顶点都在圆内**。
>
> 截图里会看到一个**很扁的椭圆**，别误认成「没裁掉的大多边形」——
> 那是沙盘圆环在掠射角下被压扁的样子。
> 取证：`node tools/ar-shots.mjs <URL>` → `tools/_ar/yaw-*.png`。

#### ③ 裁剪：只显示照到的那一块

每帧对每个锚点算一个 NDC 边距：

```
score = min(1 - |ndc.x|, 1 - |ndc.y|)
  > 0 → 在画面内（= 1 是画面正中心）；< 0 → 出画
相机后方的锚点直接判 -Infinity，避免透视除法翻号
```

**为什么用滞回**：陀螺仪有噪声，标点恰好在视锥边缘时会逐帧闪烁（一亮一灭）。
进入阈值 `+0.02`、退出阈值 `-0.10`，中间 0.12 的死区让边缘稳定。

**为什么不用 `THREE.Frustum`**：`intersectsSphere()` 只给布尔值，做不了滞回。
这里要的是「离画面边缘还有多远」这个**连续量**。

实测（11 个地点）：

| 相机朝向 | 可见标注 | 可见集合均值 x |
|---|---|---|
| 正对中心 | 11 / 11 | +0.11 |
| 向左转 45° | **4 / 11**（张家界 崀山 雪峰山脉 沅水） | **−0.55** |
| 向右转 45° | **3 / 11**（岳麓山 衡山 湘江） | **+0.66** |
| 左/右转 90°、背对 | 0 / 11 | — |

最左标点（雪峰山脉 x=−0.617）只在**左转**时可见；
最右标点（湘江 x=+0.772）只在**右转**时可见 —— 正是需求举的例子。

#### 两个「别处覆写 .visible」的坑

1. 底部「隐藏地形 / 隐藏标签」按钮原来直接写 `markers[i].visible`，
   会被下一帧的裁剪结果覆盖回去（按钮点了没反应）。
   现在按钮只翻**主开关**（`terrainOn` / `labelsOn`），
   每帧由 `visible = 主开关 && 视野内` 统一算。
2. 视野高亮网格原来是**每帧 dispose + 新建 geometry**。
   60 fps 下就是每秒 60 次几何体分配，GC 压力明显。
   现在顶点写进**预分配的 Float32Array**，只用 `setDrawRange` 控制画多少个 —— 零分配。
   配套要 `frustumCulled = false`：原地改顶点不会重算包围球，
   留着视锥剔除会因为包围球过期而把网格错误地剔掉（时隐时现）。

#### ③-b 遮挡剔除：锚点躲在山背后时，标签也必须消失

标签是 `depthTest:false` + `renderOrder:999`，**永远画在最上层**。
好处是不会被地形切掉半张（可读性好），代价是「锚点在山背后、标签却浮在山脊上」
—— 那会让「绑定在沙盘实体上」这个核心感知直接破功。
（打开 `depthTest` 不是解法：那会把标签切成半张。）

**做法**：从相机沿视线向锚点**步进**，逐步比较「射线高度」与「地形高度」。

```
OCC_STEPS = 48        // 48 步 × 11 锚点 = 528 次查表/帧，可忽略
进入遮挡：地形高出视线 > 8 mm
解除遮挡：地形高出视线 < −4 mm      // 死区 12 mm ≈ 3 px
t 取 [0.02, 0.98]     // 不取满：锚点就在地形面上，t→1 会把自己判成遮挡物
```

**⚠️ 为什么不用 `raycaster.intersectObject(terrain)`**：地形是 256×292 ≈ 15 万个三角形。
11 个锚点 × 60 fps ≈ 每秒 1 亿次三角形求交，帧率会直接塌掉。

**⚠️ 判据必须用「高度」，不能用「距离」**（这条踩过）：
第一版用「网格首交点比锚点近 5 mm」当判据，那是距离 ——
掠射角下 5 mm 距离只对应亚毫米的高度差（0.1 rad 时 0.5 mm 起伏即可凑出 5 mm 距离差），
于是把 1 mm 的起伏也报成遮挡。实测把**衡山**（视线只在地形上方 **4.1 mm**，其实可见）
误判成「被遮挡」。改判据后真正的遮挡只有**沅水**（地形高出视线 **9.4 mm**）。

**双方法互验**：`heightAtUv`（双线性查表，便宜）vs `terrainYAt`
（竖直射线打三角网格，精确）—— 3 个朝向下**逐项一致（25/25）**，
说明那个便宜的近似可以替代网格。

**⚠️ 滞回是必需的**：衡山那种 4 mm 余量贴着阈值，陀螺仪 0.2° 的噪声
（2 m 处约 7 mm 横向位移）足以让它逐帧一亮一灭。

#### 点选：必须先打标签，再退回打地形

原来 `pickAt()` 只对**地形**做射线，拿命中点的 UV 找最近地点。
标签抬高 `0.085 m`，掠射角下这个抬升把「标签背后的地形 UV」推离锚点很远：

| 现象 | 数量 |
|---|---|
| 完全没选中（超出 UV 上限 0.12 ≈ 34 cm） | 4 |
| **选中了相邻的错误地点** | 5 |

后者更严重：用户点「衡山」的标签，弹出的却是「岳麓山」的信息 ——
比点不动更伤信任。

**修法**：先 `raycaster.intersectObjects(visibleLabels)`（**只打本帧可见的**，
被裁剪或被遮挡的标签在屏幕上根本看不见，不该还能点中），
打不中才退回打地形。用户点的是标签，标签就该是命中目标。

修后实测 **`10/10`** 必中自己的地点；旧行为作为**负对照**保留在测试里（只对 `1/10`）。

> ⚠️ `R.lastPickSource` 会记下这次是 `label` / `terrain` / `terrain-miss`。
> 只报「弹出了什么」无法区分「打中标签」和「凑巧打中地形」。

#### ④ 的不变式随之扩展（不要退回旧写法）

原来 ④ 的判据是 `visible === rendered`。加了遮挡剔除之后这个等式
**不再成立也不该成立**：锚点被山挡住时 `visible = true`（确实在画面内）
但 `rendered = false`（不该画）。旧等式会把这种**正确行为**
报成「有别的代码在覆写 `.visible`」。

```
rendered === (arCull ? visible : true) && !occluded
```

即 `rendered = false` 必须能由「出画」或「被遮挡」之一解释完；
出现**第三种原因**才是真信号。

### 桌面 / 预览环境怎么「看效果」（无相机 + 无陀螺仪）

**问题**：`ar-gyro-demo.html` 原本在两条路径上都是**硬依赖真机**——
`getUserMedia` 失败就 `return`（整页卡在 loading，什么都不渲染），
而陀螺仪在桌面浏览器上根本不存在。于是「先跑起来看看效果」这件事
在笔记本上**做不到**：打开就是一片黑，会让人误判成「代码坏了」。

**改法**（三处，都在同一个文件里）：

| 环节 | 原来 | 现在 |
|---|---|---|
| 相机打不开 | `catch` 里直接 `return` → 页面空白 | 拆出 `openCamera()`，返回布尔；失败时显示「**无相机继续（桌面演示）**」按钮，点它照常进主流程 |
| 无陀螺仪 | 只有一句 flash 提示，画面永远不动 | 3 秒兜底**自动打开「拖动转视角」**，并收起那条永久停在屏幕中央的「正在读取陀螺仪…」 |
| 转视角 | 只能靠 `aimAt()`（测试专用导出） | 底部加「**拖动转视角：开/关**」；画面上拖动 = 转平板，方向键微调，`R` 回正，`L` 开关 |

⚠️ **「拖动转视角」不是另写一套相机逻辑**。它和 `aimAt()` 共用同一个 `setAim(yaw, pitch)`：

```
aimAt(yaw, pitch)  ─┐
                    ├─→ setAim(yawDeg, pitchDeg) ─→ overrideQuat ─→ render()
nudgeLook(dY, dP)  ─┘
```

两处各写一份三角函数的话，改一处漏一处 —— 这是本项目反复踩过的坑。
语义也保持一致：`yaw = 0` 看向沙盘中心，`> 0` 向左转；`pitch` 是向下俯角，
传 `null` 表示沿用「看向中心」的俯角。

**手动模式会接管姿态**：`overrideQuat` 在 `render()` 里优先级最高，
所以拖动期间陀螺仪数据被忽略；`setManualLook(false)` 释放覆盖，交还陀螺仪。
同时 `setManualLook` 会收起 `#alignhint` —— 手动模式下姿态由拖动决定，
「正在读取陀螺仪并锁定视角…」这条提示本身就是错的。

### 云台（台子）两轴旋转：位置与朝向关系

现场约束（2026-10-14 确认）：**pad 固定在台子上，台子底座不动**；
台子本身可操作，能绕**竖直轴**水平转、绕**水平轴**上下转。
所以这不是「手持平板」，是一个**两轴云台**。这条约束直接决定了
相机位置是**常量**还是**变量**。

#### 唯一不动的点：两轴交点

刚体绕一根轴转，轴上的点不动。台子有两根轴 ⇒ **两轴的交点**
是整台设备上唯一完全不动的点（底座固定 ⇒ 交点世界坐标恒定）。于是

```
camPos(θ, φ) = pivot + R_y(θ) · R_x(φ) · off
camQuat(θ, φ) = R_y(θ) · R_x(φ) · qMount
```

| 符号 | 含义 |
|---|---|
| `pivot` | 两轴交点（世界坐标），**恒定** |
| `off` | 交点到 pad **光心**的偏移，在俯仰台零位局部系里量 |
| `θ, φ` | 台子的水平转角 / 上下转角 |
| `qMount` | 零位安装四元数（零位光轴水平时 = 单位四元数）|

**关键结论**：
- **朝向只由两个角度决定，与 `off` 无关**；
- **位置完全由 `off` 决定**：
  - `off = 0` → `camPos ≡ pivot`，转多少度都不动 ⇒ **纯旋转（3DoF）**，
    现有的陀螺仪代码**一行都不用改**；
  - `off ≠ 0` → 相机沿圆弧平移，平移量 `2·|off|·sin(Δθ/2)`。

#### 为什么 `off` 必须建模、不能默认它是 0

虚拟相机的位置必须和真实相机一致，否则 AR 标注会**贴着画面漂**。
量化：`off` 造成横向平移 Δ 时，深度 L 处的标点角误差 ≈ Δ/L。

> 实测：`off = (8, 5, −3) cm`（|off| = 99 mm）→ 水平转 180° 光心横移 **171 mm**；
> 折算到 2.00 m 深的地物是 **4.88°**，水平视场 65° 铺 1152 px 时约 **87 px**。
> 87 px 的偏移是肉眼一眼能看出来的。所以 `off` 要么**设计成 0**，
> 要么**建模补偿**，没有第三条路。

⚠️ 注意**光心 ≠ 平板中心**：后摄一般偏在平板一角/一边，两者差可达 10 cm 级。
装夹时要用「后摄镜头」而不是「平板中线」去对交点。

#### 两种驱动方式

| 方式 | 位置来源 | 朝向来源 | 用途 |
|---|---|---|---|
| `manual` | 两轴角度 | 两轴角度 | 运动学演示 / 自动化验证 |
| `gyro` | **陀螺仪姿态增量** | 陀螺仪（现有链路） | **真机** |

`gyro` 方式**不需要在台子上加编码器**，用同一个陀螺仪就能把位置推出来：

```
Δq    = q_now · q_align⁻¹        （与 alignQuat 同源，同一个传感器）
camPos = pivot + Δq · r0         r0 = camPos_align − pivot
```

推导：位置 = `pivot + R·off`，而 `R = Δq·R_align`，
于是 `pivot + Δq·(R_align·off) = pivot + Δq·r0`。∎
只用到「对齐时刻的位置」这一个已知量 —— **不需要知道 `off` 本身，
也不需要知道 `qMount`**，台子的装配公差不用测量。
`off = 0` 时 `r0 = 0`，该式退化为 `camPos ≡ pivot`，与原有代码完全等价。

> ⚠️ **基准必须在「位姿已知」的那一刻标定。**
> `r0` 的语义是「此刻光心 − 交点」，所以要先把台子摆到**零位**再标定
> （那里位置 = `pivot + off`、朝向 = 单位四元数，两个量都确定）。
> 带着一个转过角度的陈旧姿态去标定，`r0` 就会带上一段多余的平移，
> 之后**每一帧位置都是错的**。实测后果：本该位置恒定的 `off = 0` 也漂了 80 mm。
> 代码里因此把 `captureGyroPosRef()` 放进了 `alignNow()`。

#### 旋转顺序不能反

必须是**外轴(偏航) × 内轴(俯仰)** —— 俯仰台挂在偏航台上。
反过来（先俯仰再偏航）会让水平轴跟着倾斜，得到的是球铰不是云台。
回归里用一条**顺序指纹**把它区分开：对 `R = R_y(θ)R_x(φ)`，
相机右向量 `= R_y(θ)·(1,0,0) = (cosθ, 0, −sinθ)`，
**与 φ 无关**；而反向顺序下它会随 φ 变化。实测固定 `yaw=45°` 扫 5 个 pitch，
右向量最大变化 `1.1e-16`（数值零）。

同一条性质还给出**「两轴云台不产生滚转」**：`right.y ≡ 0`（实测 `2.8e-17`）。

#### 两条要特别注意的

**① 判定轴取 max 不取 min。** `score = min(1-|ndcX|, 1-|ndcY|)`，
取 `min` 等价于取 `|ndc|` 的 **max** —— 所以决定「什么时候隐藏」的是
绝对值**较大**的那个轴。我第一版按「取小就是最紧的」直觉写成 `min(|ndcX|,|ndcY|)`，
把「出画面 58 px 才消失」报成了「0 px」，结论完全反了。
**判据要照着 `score` 的定义推，不能凭直觉。**

**② 闭环误差要区分「几何误差」和「遮挡」。**
锚点就落在地形网格面上（Δy = 0.00 mm），所以过锚点屏幕像素的射线
**必然穿过锚点**；若 `hits[0]` 不是锚点，只能是**被更近的地形挡住了**。
第一版把两者混在一起报「叠加误差 0.217 m」，其实是「沅水被山体遮挡」——
差点把遮挡误判成几何不准。

**③ 遮挡判据要统一到「高度」，不能用「距离」。**
同一件事第二次踩：审计时用「网格首交点比锚点近 5 mm」判遮挡，
把**衡山**（视线在地形上方 4.1 mm，可见）误判成被遮挡。
掠射角下距离阈值对高度差是**放大**的（0.1 rad 时放大 10 倍），
所以距离判据在掠射角下过敏。**先想清楚判据的量纲再写。**

### 实物沙盘是起伏模型时的垂直比例对齐

实物沙盘形态已确认为**起伏模型**（不是平面）。这决定了 ② 里最要紧的一件事：
**虚拟地形的垂直比例必须和实物一致**，否则**整个叠加都贴不上** ——
不只是标注错位，虚拟地形本身就与实物对不上。

#### 当前比例

| 项 | 值 | 来源 |
|---|---|---|
| 水平比例 | `1:196,071` | 2.80 m ↔ 湖南经向跨度 549 km |
| 垂直比例 | `1:12,272` | 169 mm ↔ 声明上限 2076 m |
| **垂直夸张** | **`16.0×`** | 垂直比例 / 水平比例 |
| 实际渲染峰高 | `142.2 mm` | 数据实际最大 1745.2 m（不是 2076） |
| 峰高 / 直径 | **`5.08%`** | 2.8 m 沙盘即 142 mm |

> **垂直夸张与沙盘尺寸无关**：`reliefM` 与 `tableW` 同比缩放，
> 所以 1.8 m 和 4.0 m 的沙盘夸张倍数都是 `15.98×`（已用 5 个尺寸实测）。
> 唯一的调节旋钮是 `reliefScale`。

#### 现场怎么对齐：只要量一个数

**实物沙盘上最高点高出基准面多少毫米**（基准面 = 模型最低的平坦面）。

填进设置面板「实物峰高」→ 点「按实物峰高对齐起伏」即可。
原理是峰高**严格正比**于 `reliefScale`，可以直接反解：

```
reliefScale = 实测峰高 / (reliefScale = 1 时的峰高)
```

实测（`relief-match-test.mjs`）：输入 60/100/142/200/300 mm，
渲染出的峰高分别就是 60.0/100.0/142.0/200.0/300.0 mm（误差 < 0.5 mm）。

**目测速查**：虚拟峰高 = 直径的 5.1%。2.8 m 沙盘上最高点应该是 **142 mm**。
拿这个比例先目测核对，再决定要不要动 `reliefScale`。

#### ⚠️ 一个前提

上面的做法假定实物模型是**同一套 DEM 的等比起伏**。
如果实物是手工艺术化造型（峰被压扁、丘陵被抬高），
**单一 `reliefScale` 只能整体逼近，无法逐点吻合** ——
那种情况建议把标注放在基准面上（`reliefScale ≈ 0`，实测锚点会全部落到同一平面），
不要跟随虚拟起伏，否则标注会随地形起伏而无规律地偏移。

#### 为什么必须对齐：量化

垂直偏差 `e` 在深度 `L`、仰角 `θ` 处投影成屏幕错位 ≈ `e·cosθ/L`：

> `e = 50 mm`、`L ≈ 2.08 m`、`θ = 15.6°` ⇒ `0.0232 rad ≈ 1.33°` ⇒ **约 24 px**

即 50 mm 的比例失配就有约 24 px 的可见错位。2.8 m 沙盘若把 142 mm 做成 100 mm，
失配 42 mm ⇒ 约 20 px；做成 200 mm，失配 58 mm ⇒ 约 28 px。

### 地形数据：三个容易改错的地方


跑 `python tools/check-sites.py` 可以把下面这些数全部打印出来（带一个可选参数按真实沙盘宽度算）。

#### ① 「声明上限 2076 m」不等于「数据最大 1745 m」—— 不要把它「修正」掉

```
terrain-meta.json  elevation_max_m = 2076.0     ← 原始 DEM 的高程上限
terrain-height.f32 实际最大值      = 1745.19     ← 重采样到 256×292 后，孤立尖峰被平滑掉了
```

页面用 **2076** 归一化（`e / MAX_ELEV * reliefM`），这是**对的**：它保持**绝对高程比例**
（真实 300 m 的山就渲染成 300/2076 的相对高度）。
若顺手「修正」成 1745，整片地形会被整体抬高 **19%**，虚拟地形与真实地貌的高程关系就错了。
代码里已加注释说明，别动它。

#### ② 山峰被系统性压低，平原与湖区准确

约 **2.4 km/格** 的网格，孤立尖峰被邻域平均拉平：

| 地点 | DEM 采样 | 实际 | 倍率 |
|---|---|---|---|
| 岳麓山 | 90.6 m | 300.8 m | 0.30 |
| 衡山 | 506.4 m | 1300.2 m | 0.39 |
| 崀山 | 315.4 m | ~818 m | 0.39 |
| 洞庭湖 | 26.3 m | 26~33 m | **≈1.0 ✓** |
| 澧阳平原 | 38.8 m | ~40 m | **≈1.0 ✓** |

关键是**相对结构基本保留**（岳麓山/衡山 = 0.18 vs 实际 0.23），所以视觉上的高低起伏
交给设置里的 **`reliefScale`（地形起伏倍数）** 去调，不需要改 DEM。
但要注意：**介绍卡里的文案写的是真实高程**（如「岳麓山 300.8 米」），
与地形渲染出来的高度不是同一个量 —— 别拿它们互相印证。

#### ③ `tableW` 必须等于**真实沙盘的物理宽度**

```
虚拟地形张角 = 2·atan((tableW/2) / camDist)
真实沙盘张角 = 2·atan((W_real/2) / d_real)
```

两者不等，叠加就会整体错位（缩放错，越靠边越明显）。
所以这个值**不是随手可改的显示参数**，现场校准要照着尺子量出来的宽度填
（设置面板里有「沙盘宽度」滑块）。

> 这里踩过一次「两个真相来源」的坑：`tools/check-sites.py` 里曾硬编码
> `TABLE_W = 2.40`，而页面 `P.tableW` 默认 `1.80` —— 两个值悄悄分叉，
> 脚本打印的「世界X / 世界Z」和页面实际渲染的对不上。
> 现在脚本改为**从页面读取** `P.tableW` 与 `TERRAIN_ASPECT`，并支持命令行传入真实宽度：
>
> ```
> python tools/check-sites.py 2.40      # 按量出来的真实沙盘宽度算
> ```

### 漂移处理（⚠️ 先搞清楚「漂移」是什么）

**`alpha - alignAlpha` 不是漂移。** 你转动平板，alpha 一样会变。
把「偏转角 ÷ 时长」当漂移率，一转平板就会报出 `-3.9 °/min` 甚至 `741 °/min` 这种数字 ——
它测的是「你头转得多快」，不是「陀螺仪漂了多少」。**用这个数判断方案可行性会得出完全错误的结论。**

真漂移只能这样测：用相邻事件的 alpha 差分估角速度，
**只有角速度低于 2 °/s（设备确实静止）时**，alpha 的缓慢变化才计入漂移样本。

所以顶栏「**静止漂移**」格的含义是：

| 显示 | 含义 |
|---|---|
| `采样中 3s` | 静止样本不足 4 秒，还不给结论（正常，刚进来时会这样）|
| `0.08 °/min` | 真正的陀螺零偏漂移率，绿色 < 0.3 / 黄色 < 2 / 红色更高 |

报告里同时给几个量，**别混用**：

| 字段 | 含义 |
|---|---|
| `staticDriftPerMin` | **静止漂移率**，唯一可用于判断方案可行性的数 |
| `staticSampleSec` | 静止样本时长（可信度）|
| `sampleCoverage` | **采样覆盖率** —— 低于 15% 时上面的漂移数字不可信（原因见下文「低功耗门控」）|
| `orientHzPeak` | 瞬时频率峰值，说明传感器在需要时能跑多快 |
| `yawFromAlignDeg` | 相对对齐时刻的**偏转角**，转动 + 漂移的混合，**不是漂移** |

**漂移归零** —— 把当前设备姿态当作首次对齐时的姿态。
数学上是 `qNow · alignQuat_new = qDev₀ · alignQuat₀`，
**只适用于平板本身没被动过、纯粹是陀螺仪漂了**的情况。
**重新对齐** —— 把地形中心拉回当前视线中心，适合手持自由旋转。

> **漂移换算成像素**（65° 水平视场 / 1152 px，1° ≈ 17.7 px）：
> `0.08 °/min` → 1 min 后 1.4 px（看不见）；`1 °/min` → 1 min 后 17.7 px（能看出）；
> `4 °/min` → 1 min 后 70 px（明显错位）。
> 所以「静止漂移 < 0.3 °/min」这个绿色阈值不是随便定的。

### ⚠️ 低功耗门控：3DoF 方案最需要知道的一件事

**Android 在设备静止时会把 `deviceorientation` 降到约 1 Hz，转动时才升频。**

第二次实测最能说明问题：124 秒只有 102 个事件 = **0.82 Hz**，平均间隔 **1.22 秒**。
而第一次在转动中测到 12.9 Hz，峰值超过 60 Hz。

这一条事实会同时引发两个问题，都已经处理：

#### 问题一：漂移采样被大量丢弃（已修）

原来的采样条件写的是「事件间隔 ≤ 0.6 秒才计入」，
但真实间隔是 1.22 秒 —— **94% 的样本被丢掉**，
124 秒里只累计到 **7.4 秒**静止样本。这个数字算出来的漂移率毫无意义。

修法：把间隔上限放宽到 **5 秒**。放宽是安全的，因为判据是**角速度**而不是间隔 ——
真正需要防的只是「长时间断流后的姿态跳变」，那种情况角速度很大，会被判成转动。

回归测试里专门复现了这个场景（1.2 秒间隔派发）：

```
[PASS] 低功耗间隔也能累计样本（不再被丢弃）  (stillMs +19295（期望 ≈20000）· 丢弃 +0)
[PASS] 低功耗下漂移量估算仍准确              (+0.0322° 期望 ≈0.0333°)
```

#### 问题二：视角更新会一跳一跳（已修）

传感器 1 Hz 意味着视角每秒只更新一次，观感很卡。

修法：**姿态平滑** —— 用 `slerp` 按帧率做指数平滑，
时间常数由设置里的「姿态平滑」滑块控制（默认 140 ms，设 0 则直通可对比）：

```js
const k = 1 - Math.exp(-dtSec * 1000 / P.smoothMs);   // 时间无关，帧率变化不影响手感
cam3.quaternion.slerp(qGoal, k);
```

**必须用时间无关的系数** —— 固定系数在不同帧率下手感会变。

#### 问题三：平滑只能掩盖，不能凭空生成运动（根本解）

平滑让 1 Hz 的更新看起来顺一点，但**传感器 1 秒才给一个新姿态，
这 1 秒里平板转到哪了，程序是不知道的** —— 转动时画面依然跟不上。

根本解是引入高频数据源：**`devicemotion` 的 `rotationRate`（角速度）**。
它和 `deviceorientation` 来自同一套 IMU，但频率高得多。

做法是「绝对姿态校正 + 高频积分推进」：

```
deviceorientation 到来（~1 Hz，绝对无漂移）→ 用绝对姿态【重置】qBase
devicemotion 到来（~60 Hz，角速度）        → 用角速度【积分推进】qBase
```

每次绝对姿态到来都把积分结果校正回来，所以**既高频、又不累积漂移**。

**实现上有一个必须注意的分层**：姿态要拆成「基座」和「修正」两层。

```js
/* qBase：设备系 → 世界系，【不含】q1 / q0 修正 */
const qBase = new THREE.Quaternion();

function resetBaseFromOrient() {          // deviceorientation 到来时
  qBase.setFromEuler(_e2.set(b, a, -g, 'YXZ'));
}
function onMotion(e) {                    // devicemotion 到来时
  const rr = e.rotationRate;
  _w.set(degToRad(rr.beta), degToRad(rr.gamma), degToRad(rr.alpha));  // 设备本体轴
  const len = _w.length();
  if (dt > 0 && len * 57.29578 < 1500) {  // 只按【角速度】挡异常跳变
    _dq.setFromAxisAngle(_w.divideScalar(len), len * dt * motionGain);
    qBase.multiply(_dq);                  // 右乘 = 本体坐标系中的旋转
  }
}
function readDeviceQuat(out) {            // 最终姿态
  out.copy(qBase);
  out.multiply(q1);                       // 相机朝设备背面的约定
  out.multiply(q0.setFromAxisAngle(zee, -degToRad(screenAngleDeg())));  // 屏幕旋转补偿
  return out;
}
```

> **为什么必须分层**：`rotationRate` 的轴是**设备本体轴**，
> 而 `q1`（相机约定）和 `q0`（屏幕旋转补偿）是**固定补偿**。
> 如果把它们卷进积分，每一帧都会把这两个固定补偿也「转」一次，姿态会越积越歪。

> **别用「角度增量」做异常跳变保护**：低功耗门控下事件间隔可达 1 秒，
> 正常的 90 °/s 转动就会产生 1.57 rad 的增量，用增量阈值会把正常转动也丢掉。
> 按**角速度**挡才安全（人转动很少超过 1500 °/s）。

#### 融合的方向正确性必须实测

`deviceorientation` 的 alpha/beta/gamma 是 **Z-X'-Y'' 内旋欧拉角**，
而 `devicemotion` 的 rotationRate 是**本体轴角速度** ——
两者的轴定义不是一回事，方向或符号搞反会让姿态越转越歪，**比不加融合更糟**。

所以专门写了 `tools/motion-fusion-test.mjs`：用「设备平放」这个已知姿态做基准，
喂已知角速度，检查旋转结果。实测**误差全部 0.0000**：

```
绕设备 X 轴 +300°/s × 0.1s →  设备 Z 轴 (0,0,1) → (0.000, -0.500, 0.866)  误差 0.0000
绕设备 Y 轴 +300°/s × 0.1s →  设备 Z 轴 (0,0,1) → (0.500,  0.000, 0.866)  误差 0.0000
绕设备 Z 轴 +300°/s × 0.1s →  设备 Z 轴 (0,0,1) → (0.000,  0.000, 1.000)  误差 0.0000
绕设备 X 轴 -300°/s × 0.1s →  设备 Z 轴 (0,0,1) → (0.000,  0.500, 0.866)  误差 0.0000
分 10 步走完 30°            →  与单步结果一致                              误差 0.0000
```

最后一项验证的是**四元数右乘的复合性** —— 分步积分必须和单步等价。

**设置面板里有「运动融合：开/关」开关**，可以现场 A/B 对比
「融合开（跟手）」和「融合关（1 Hz 卡顿）」的差别。

#### 报告里的「采样覆盖」就是为这件事加的

| 字段 | 含义 |
|---|---|
| `sampleCoverage` | 有效样本时长 / 总时长。第二次实测只有 **6%** |
| `effectiveSampleSec` | 有效样本时长（第二次只有 7.5 s）|
| `droppedSamples` | 因间隔过长被丢弃的样本数 |
| `orientHzPeak` | 瞬时频率峰值，用来说明「传感器在需要时能跑多快」|

> **覆盖率低的时候，「静止漂移 0.00」只能说明「没测到」，不能说明「没有漂移」。**
> 报告里覆盖率 < 15% 会直接标红提示可信度有限。

### ⚠️ 「进入一瞬间模型转了一下」—— 两个叠加的原因

**症状**（真机录屏，11.12 s / 1152×720 / 24fps）：

| 时间 | 现象 |
|---|---|
| 2.8 ~ 3.8 s | 「未对齐」状态，地形斜贴在真实桌面上，透视正确 —— 看着是对的 |
| **4.0 s** | 顶部弹出「已自动对齐」，**地形在同一瞬间转掉约 16~45°** |
| 4.2 s ~ | **稳定在新姿态，不再变化**（说明是一次性的，不是传感器漂移） |

拉密帧后可以确认：**跳变与「已自动对齐」提示是同一帧发生的**，而且**背景里的真实房间没有动**
（设备没转），所以是虚拟相机被转了一下。

原因有**两个**，互相叠加：

#### 原因 A：`setFromUnitVectors` 只约束光轴，滚转是「顺带」的

对齐必须同时决定两件事 —— 光轴指向、以及**绕光轴的滚转**。原实现只决定了前者：

```js
/* ❌ 旧写法 */
alignQuat.setFromUnitVectors(new THREE.Vector3(0, 0, -1), bLocal);
```

`setFromUnitVectors` 给的是**绕 `(0,0,-1) × bLocal` 的最小旋转**。
听上去「最小旋转 = 不带多余滚转」，其实不是：

> 它是**绕光轴零扭转（swing）**，而「零扭转」不等于「滚转正确」。
> 当 `bLocal` 有偏离「光轴–设备 up 所在平面」的分量时（也就是设备需要带一点偏航才能对准），
> 这个 swing 会把相机 up 甩出去。**设备越偏离正对，歪得越离谱。**

实测（`tools/align-roll-test.mjs`，同姿态下新算法 vs 旧算法）：

| 设备姿态 (α β γ) | 旧算法滚转误差 | 新算法 |
|---|---|---|
| 0 0 0（水平正对，纯俯仰） | 0.00° | 0.00° |
| 0 30 0（前后倾，纯俯仰） | 0.00° | 0.00° |
| 0 0 25（左右倾） | **15.75°** | 0.00° |
| 0 35 25 | **6.55°** | 0.00° |
| 45 20 −15（带偏航） | **7.28°** | 0.01° |
| 120 60 30 | **74.59°** | 0.00° |
| −80 55 −40 | **21.02°** | 0.01° |

注意前两行：**纯俯仰时旧算法完全正确** —— 这也解释了为什么它不是每次都能复现，
只有设备带侧倾 / 偏航时才会歪。搜索 504 个姿态后，旧算法最坏可达 **74.8°**。

**修复**：在**设备坐标系**里做一次 `lookAt`，把 up 钉在设备 +Y：

```js
/* ✅ 新写法 */
_m4.lookAt(ORIGIN, bLocal, UP_Y);
alignQuat.setFromRotationMatrix(_m4);
```

可以证明这样得到的相机 up 恰好等于「设备 up 在垂直于光轴平面上的投影」，
滚转误差恒为 0，而且**用户转动平板时虚拟地平线与真实相机画面同步倾斜**（这才是 AR 该有的行为）。

**为什么不能用「相机 up 与设备 up 的夹角」当判据**（我一开始就是这么写的，错的）：
设备的 up 一般**不在**垂直于光轴的平面内，纯俯仰修正也会改变这个夹角 ——
「水平正对」姿态就能报出 **63.9°** 的假误差。那是俯仰，不是滚转。
正确判据必须先把设备 up **投影到垂直于光轴的平面**上再比夹角。

#### 原因 B：**「延迟 1.2 秒再对齐」这个流程本身**（这才是修完 A 之后仍然存在的那个）

修好 A 之后真机再测，进入瞬间**还是**会转一下。因为对齐前后用的是**两套不同的滚转约定**：

| 阶段 | 相机 | 滚转基准 |
|---|---|---|
| 对齐前 | 固定视角 `lookAt(中心)` | **世界竖直**（up = 世界 +Y） |
| 对齐后 | `readDeviceQuat() · alignQuat` | **设备 up** |

两者都指向地形中心，所以**差别只在滚转**。而设备只要有侧倾，这两套就差那么多度 ——
原来 `maybeAutoAlign` 延迟 **1200 ms** 才对齐，等于让用户盯着一个滚转不对的模型看 1.2 秒，
然后眼睁睁看它转过去。**延迟本身就是症状的来源。**

**修复**：干脆不给中间态。

```js
/* 第一次拿到姿态就对齐 —— 不要延迟。
   启动页第 1 步已经要求「把平板装到支架上、镜头对准沙盘中心」，
   也就是进入之前就已经对准了，所以第一次拿到姿态就是最佳对齐时机。 */
function onOrient(e) {
  ...
  resetBaseFromOrient();          // 必须先重置基座，对齐要读 qBase
  if (first) { flash('陀螺仪已就绪'); alignNow(true); }
}
```

配套两条，缺一不可：

1. **对齐前不渲染模型**（`render()` 里 `if (!aligned && !fallbackShow) { renderer.clear(); return; }`）。
   否则用户还是会先看到一个滚转不对的模型。
   （陀螺仪 3 秒不来的兜底：按固定视角把模型显示出来，总比空白好。）
2. **对齐那一刻直接吸附，不走 slerp**（`snapPose` 标志）。
   否则第一帧还会从旧姿态平滑过去 —— 等于把「一次跳变」换成「一次 140 ms 的滑动」，照样是「转了一下」。

顺手还修了一个同类问题：**屏幕方向变化**（系统自动旋转）会让 `q0` 补偿跟着变，
模型会莫名其妙转 90°。现在监听 `orientationchange` 并保持当前相机姿态：
`alignQuat = qNow⁻¹ · camQuat`，`camQuat` 一帧都不变。

### 横屏下陀螺仪角度是怎么映射的（含一次「补丁本身是 bug」）

平板是**横屏**用的，`screen.orientation.angle` 是 **90 / 270**，而陀螺仪给的是
**设备本体坐标**下的欧拉角。两者之间差一个「屏幕旋转补偿」，这一步错了模型就整体歪 90°。

完整链路（`readDeviceQuat()`）：

```
deviceorientation(α, β, γ)
  → qBase = Euler(β, α, −γ, 'YXZ')      设备本体姿态（devicemotion 积分也只作用在这一层）
  → × q1  = Rx(−90°)                    相机朝设备背面的约定
  → × q0  = Rz(−o)，o = screen.orientation.angle    ← 屏幕旋转补偿，横屏的关键就是这一步
```

**这条链路已用「独立参照物」逐分量验证过**（`tools/landscape-map-test.mjs`）：

| 项 | 结果 |
|---|---|
| 28 个采样（7 姿态 × 4 屏幕角 0/90/180/270）下，页面姿态 vs W3C 规范公式 | **最大偏差 0.0000°** |
| 该偏差是否等于单位四元数（即逐分量一致，而非只差一个固定旋转） | **0.0000°** ✅ |
| 页面是否真读到了被覆盖的屏幕角（防止测试空转） | o=0/90/180/270 全部读到 ✅ |
| 负对照：漏掉 `q0`（把 o 当 0）会怎样 | 漂 **180.000°** ✅ 判据抓得住 |
| 物理不变量：平板在平面内转 φ、系统把 o 也改 φ → 相机应逐位不变 | **最大偏差 0.0000°**（28 组） |

参照物用的是 W3C 规范公式，`M = Rx(−90°)`、`q0 = Rz(−o)`：

```
R_enu = Rz(α)·Rx(β)·Ry(γ)        设备 → 东北天
相机（页面世界）= M · R_enu · q0
```

> 参照公式本身也先验证过（`tools/reference-formula-check.mjs`，纯数学 < 1 秒）：
> 把 7 个候选公式都算一遍，看哪个能让 `K = Q_page · Q_ref⁻¹` 恒定。
> 结论是 `M(−90°)·Rz(α)Rx(β)Ry(γ)·q0` **与页面实现逐分量一致**；
> 而把 `q1` 也塞进参照的写法会随姿态漂到 166°+ —— **参照公式写错就会得出假结论**，
> 所以这一步不能省。

#### ⚠️ `keepPoseAcrossScreenAngle` 这个「防跳」补丁是错的，已删除

原来 `orientationchange` 时会执行 `alignQuat = qNow⁻¹ · camQuat`，号称「锁住姿态防模型转 90°」。
**它恰好会在「平板横屏固定在支架上」这个场景里出错：**

1. **相机必须等于屏幕内容坐标系。** 只有这样，渲染出来的画面画进内容坐标系才是对的。
   屏幕方向一变，内容坐标系在房间里转了 −Δ，**相机也必须跟着转 −Δ**。
   用户此时**看不到任何变化** —— 因为内容坐标系也转了，两者相抵。
2. 强行把相机锁住不动，相机就不再等于内容坐标系，画面会相对屏幕歪掉 Δ。
   实测：设备完全不动、只把 o 从 0° 改成 90°，相机被扭了 **25.33°**
   （而且还是姿态平滑半途采样的中间值），而正确值应该是「跟着转 90°、用户无感」。
3. 设备**真的在平面内转了 φ** 时，规范公式本身就给出「相机逐位不变」的结果
   （见上表最后一行），**根本不需要这个补丁**。

删除后 `landscape-map-test` 的最后一项从 `alignQuat 变化 25.33° / 相机偏差 25.33°`
变成 `0.0000° / 0.0087°`。现在屏幕方向变化时只重算尺寸与视场角：

```js
function onOrientationChanged() {
  setTimeout(onResize, 120);
}
```

> 教训：**「防跳」类补丁要先证明「不补真的会跳」。**
> 这里不补不会跳（相机与内容坐标系同步旋转，视觉上完全静止），
> 补了反而把相机从内容坐标系上撬开，制造出一个 90° 的歪斜。

#### ⚠️ 一个我凭直觉判错的方向：α 到底是「偏航」还是「滚转」

顺着「横屏」这条线继续查时，我盯上了页面里用 **α** 判「静止 / 转动」、
以及用 `alpha - alignAlpha` 算「相对对齐偏转」这两处，并这样推理：

```
❌ 我当时的推理：
   α 是「绕设备 Z 轴（屏幕法线）」的旋转 → 就是「平面内滚转」
   横屏（o = 90 / 270）下用户左右转平板，绕的是世界竖直轴
   → 那对应的是 β，不是 α
   → 结论：横屏下用 α 判静止是错的，用户转平板会被当成「设备静止」，
            真实转动被累计进漂移，报出假漂移
```

**推理链条看着很顺，但第一步就错了。** W3C 的

```
R_enu = Rz(α)·Rx(β)·Ry(γ)
```

是**外旋**复合 —— 矩阵乘法里最右边的 `Ry(γ)` 先作用到向量上，`Rz(α)` **最后**作用。
所以 α 是**绕世界竖直轴**的旋转，恒等于「偏航」，**与设备怎么摆、屏幕朝哪都无关**。

数值验证（`tools/reference-formula-check.mjs` 的第 3 段，任意姿态 × 任意屏幕角）：

```
o=  0°  α+10° 的旋转轴：β=  0 γ=  0 → 0.00,1.00,0.00  |  β= 45 γ=  0 → 0.00,1.00,0.00  |  β= 90 γ= 90 → 0.00,1.00,0.00
o= 90°  α+10° 的旋转轴：β=  0 γ=  0 → 0.00,1.00,0.00  |  β= 45 γ=  0 → 0.00,1.00,0.00  |  β= 90 γ= 90 → 0.00,1.00,0.00
o=180° / o=270° 同样全部是 (0, 1, 0) = 世界竖直轴
```

**所以页面用 α 判静止、用 α 差算偏转，横屏下也是对的**，我基于错误前提做的改动
已全部撤回。顺带确认：β / γ 在不同姿态下对应**不同**的世界轴（β=70 时 β 的轴是
`(0.87, 0, -0.50)` 斜轴，β=90 时 γ 的轴才是竖直轴）—— 所以它们不能当稳定判据，
只有 α 是恒定的世界偏航。

> **教训：欧拉角的「哪个角对应哪根轴」不要凭直觉判断，数值查一次只要一分钟。**
> 这里的坑在于「内旋 / 外旋」两种读法给出完全相反的结论，
> 而两种读法都常被称作「绕某轴旋转」。凡是这类问题，
> 就用「单独扰动一个角 → 看世界系增量的旋转轴」来定案。
> 这条已经固化进 `tools/reference-formula-check.mjs`，会跟着每次自检一起跑。

### 支架仰角：平板装上去必然有仰角，会不会踩到万向锁

横屏映射查完之后，还有一件**与展项安装方式直接相关**的事要确认：
平板装在支架上，屏幕不可能平放 —— 一定有仰角，也就是 `β ≠ 0`。
而 W3C 用的是**内旋 Z-X'-Y''** 欧拉序，`R_enu = Rz(α)·Rx(β)·Ry(γ)`，
中间那一步是 `Rx(β)`。**内旋欧拉序在「中间角 = ±90°」处退化**：

```
β = 90°  平板完全竖直（像一块立起来的相框）
         → α 与 γ 的旋转轴重合
         → 两个角只剩「和 / 差」有意义，各自单独失去意义
```

`β` 的含义：`0°` = 屏幕平放朝上，`90°` = 完全竖直。平板斜靠在支架上看沙盘，
大概落在 45° ~ 75° 这一带。

用 `tools/vertical-stand-check.mjs`（纯数学，不起浏览器，< 1 秒）把这件事拆成四问：

| 问题 | 结论 |
|---|---|
| ① 用户转支架看四周（绕世界竖直轴平移）在任意 β 下是否无损 | ✅ **逐位无损**（含 β=90°）。判据用四元数直接比较 |
| ② β 接近 90° 时，底层姿态的 0.5° 误差被 α 放大多少倍 | 条件数 = `1/cos(β)`：β=75° → 3.9×，β=85° → 11.5×，β=90° → ∞ |
| ③ 反解的两个分支 `(α,β,γ)` 与 `(α+180, 180−β, γ+180)` 是不是同一姿态 | ✅ **恒等** —— 传感器偶尔跳分支无害 |
| ④ 「反解 → 重建」这条链的保真度 | ✅ β ∈ [−90°, 90°] 全程 2.4e-6°（浮点噪声）；**β 恰为 ±90° 是固有奇点**，误差 4.5° |

#### 为什么 ② 的「放大 11.5×」不影响画面

页面渲染走的是 `readDeviceQuat()`：

```js
qBase.setFromEuler(_e2.set(b, a, -g, 'YXZ'));   // 由 (α,β,γ) 直接【复合】
```

**它只做复合，从不做反解。** 反解的奇点它根本不经过。
所以：

- **画面**：任意 β（含 90°、100°）都正确。已由 `tools/landscape-map-test.mjs`
  在浏览器里实测 —— 新增的三个奇点姿态在 4 个屏幕角下**全部 0.0000°**。
- **遥测**：HUD 上「静止漂移」「相对对齐偏转」这两个读数用的是 **α 这个标量**，
  在 β→90° 时会被 `1/cos(β)` 放大，读数开始乱跳。
  它不会让画面出错，但会让现场人员**误判成设备坏了** —— 这是真实成本。

#### β 恰为 90° 时反解必然丢信息（欧拉角表示的固有缺陷）

`cβ = 0` 时，α 与 γ 的两组 `atan2` 参数**同时**变成 0：

```js
alpha = atan2(-m[0][1], m[1][1])   // β=90° 时 m[0][1] 与 m[1][1] 都 ≈ 0
gamma = atan2(-m[2][0], m[2][2])   // m[2][0] 与 m[2][2] 也都 ≈ 0
```

`0/0` 无解 —— 「绕竖直轴的朝向」这份信息在 `(α,β,γ)` 表示里被**抹掉**了。
实测刀锋一样窄：β=89.99° 时误差仍是 2.4e-6°，β=90.0° 时跳到 4.5°。

页面不受影响（它不反解）。受影响的是**反解这一侧** —— 包括测试工具，
以及任何未来把姿态改成「反解成欧拉角再存」的重构。

> ⚠️ 我在写这个脚本时**连着踩了两个坑**，都值得记下来：
>
> **坑一：阈值卡到 1e-9，比浮点噪声还紧。** 实测往返噪声就是 2.4e-6°，
> 于是 ① 报了个「有损」的假失败。阈值取 1e-4。
> （同一个错在 `reference-formula-check.mjs` 里也犯过一次。）
>
> **坑二：用反解构造测试输入时，忘了 β 越过 90° 要翻分支。**
> `asin` 只能给 `[−90°, 90°]` 里的值，β=100° 会被静默反解成 80° 的**另一个**姿态。
> 于是 ④ 在 β=90° 处报出 4.5° 的假失败。
> 修法不是硬推分支公式，而是**用「重建回去比对」自我验证**，自动挑对得上那一支：
>
> ```js
> function rEnuToAngles(q) {
>   let best = decOnce(q, false), bestErr = Infinity;
>   for (const alt of [false, true]) {
>     const d = decOnce(q, alt);
>     const err = qAngleDeg(rEnu(d.alpha, d.beta, d.gamma), q);
>     if (err < bestErr) { bestErr = err; best = d; }
>   }
>   return best;
> }
> ```
>
> **坑三（更隐蔽）：③ 那一项我一开始写成了重言式。**
> 我拿同一个 `q` 反解出分支 0，再按恒等式把分支 0 变换成分支 1，然后比两者 ——
> 必然相等，什么也验不出来。要验恒等式本身，**两边都得独立构造**：
> `rEnu(a,b,g)` 直接对 `rEnu(a+180, 180-b, g+180)`。
>
> **教训：测试里凡是「A 和 B 应该相等」，先问一句「A 和 B 是不是同一个东西换个写法」。
> 如果是，这个断言是恒真的，写它只是在骗自己。**

#### 结论：支架仰角建议 β ≤ 80°

| β（仰角） | α 放大倍数 | 影响 |
|---|---|---|
| 60° | 2.0× | 遥测基本可用 |
| 70° | 2.9× | 可用 |
| 75° | 3.9× | 可用 |
| 80° | 5.8× | 遥测开始明显跳动 |
| 85° | 11.5× | 静止漂移读数乱跳（**画面仍正常**） |
| 90° | ∞ | α 完全失去意义（**画面仍正常**） |

即**平板与水平面夹角 ≥ 10°**。画面在任意仰角下都对，这条限制是为了让
HUD 读数可信、避免现场人员误判。

#### ⚠️ 还有一条只能真机验的

上面「保真」的前提是：传感器给出的 `(α,β,γ)` 来自**同一个一致的姿态**。
但部分平台是**分开融合**的：β/γ 来自加速度计、α 来自磁力计。
平板接近竖直时加速度计定不出绕竖直轴的朝向；若磁力计又被支架
（**金属件 / 扬声器磁铁**）干扰，α 就会偏 —— 这时 `(α,β,γ)` 互相矛盾，
重建出的四元数就是错的，**画面会歪**。

真机验证项：把平板摆到**实际安装仰角**，缓慢左右平移，看画面是否连续无跳变；
再把仰角改掉 20° 重试。若只在某个仰角附近跳，就是这个问题 ——
对策是换支架材质 / 位置（远离金属与磁铁），而不是改代码。

只收录 11 个地点，分布稀疏。原来「取最近地点」没有上限，
第二次实测出现了 **UV 距离 0.2846**（≈ 28% 地形宽度 ≈ 0.5 m）还照样弹卡的荒唐结果。

现在超过 **0.12**（约 20 cm）就明确提示「这里附近没有收录的地点」，
并告知最近的候选地点还有多远。

> 注意：`yawFromAlignDeg` 在第二次实测里是 **-0.1°**、`movingSampleSec` 只有 0.1 秒 ——
> 说明平板全程几乎没动过。这也解释了为什么 `staticDriftPerMin` 是 `0`：
> **静止时陀螺仪确实没有可测量的漂移**，这是 3DoF 方案的好消息。

> **`orientHz: 0` 曾经是个假警报。** 旧版报告里有个「瞬时频率」，
> 而你点「出报告」那一刻手是静止的 —— Android 静止时把传感器降到 2~7 Hz 甚至暂停，
> 最近 2 秒窗口里就是 0 个事件。**413 个事件说明传感器一直正常工作。**
> 现在 HUD 显示的是**平均频率**（`12.9 Hz 均`），报告里 `orientHzAvg` / `orientHzNow` 两个都给。

### 无人值守展项：息屏 / 显卡上下文 / 错误留痕

上面那些都在解决「**对准不准**」，下面这三件解决的是「**开一整天会不会坏**」。
它们在开发时全都看不出来，只有在展项上连续运行才会现形。

#### ① 屏幕常亮（Wake Lock）

系统默认几十秒就息屏。息屏的后果不只是「看不到画面」——
浏览器会把**传感器事件一起挂起**，唤醒时姿态有一个跳变（等于用户白对准了）。

用 `navigator.wakeLock.request('screen')`。但**两个细节漏一个，这个功能就等于没做**：

```js
async function acquireWakeLock() {
  if (!('wakeLock' in navigator)) return;
  if (document.visibilityState !== 'visible') return;
  if (wakeLock && !wakeLock.released) return;      // 已经持有
  try {
    wakeLock = await navigator.wakeLock.request('screen');
    /* ★ 浏览器释放锁时把引用置空，下次可见时重新申请 */
    wakeLock.addEventListener('release', () => { wakeLock = null; });
  } catch (e) {
    /* 低电量 / 省电模式会拒绝（NotAllowedError）—— 属正常行为，不弹窗打扰用户 */
  }
}
addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'visible') acquireWakeLock();
});
```

| 细节 | 漏掉的后果 |
|---|---|
| **切回前台要重新申请** | 浏览器切后台会**自动释放**锁。只申请一次的话，**第一次息屏之后就再也不常亮了** —— 而且「第一次有效、后面失效」这种 bug 极难发现 |
| **必须处理 rejection** | 低电量时浏览器会拒绝，这是正常行为，弹窗会打扰用户；记进报告即可 |

#### ② 显卡上下文丢失

平板长时间运行 / 切换应用 / GPU 驱动重置时，浏览器可能回收 WebGL 上下文。
默认行为是画面变空白且**不再恢复** —— 无人值守展项就废了。

**好消息**：Three.js 内部已经处理了（`onContextLost` 里 `preventDefault()` +
监听 `webglcontextrestored` 重建 GL 状态），所以不需要我们接管恢复。
我们只额外做两件事：

```js
canvas.addEventListener('webglcontextlost', (e) => {
  ctxLostN++; e.preventDefault();     // 幂等的安全网：不依赖 Three 内部实现是否变化
}, false);
canvas.addEventListener('webglcontextrestored', () => {
  ctxRestoredN++;
  onResize();                          // GL 状态被重建过，viewport 不一定还在
}, false);
```

> ⚠️ **验证「恢复后画面还在不在」不能靠 `readPixels`。**
> WebGL 规定：一帧提交之后默认帧缓冲的内容就变成 `undefined`
> （除非创建上下文时开 `preserveDrawingBuffer`）。在渲染回调**之外** `readPixels`
> 几乎必然读到全 0 —— 我第一版就是这么写的，于是报了一个假失败。
> 正确做法：**截两张不同姿态的图，看它们是否不同**。
> 上下文真的死了的话，两张都会是同样的空白 → 字节完全相同。

### 现场判据：让真机测试一轮答完所有未知项

部署展项时有两个问题**只能到现场才知道答案**，而且都决定「要不要动手调整」。
把它们做成页面自带的判据后，真机跑一轮就能拿到结论，不用来回问。

#### 判据一：支架仰角落在安全区吗

画面在任意仰角下都正确（见上文「支架仰角」一节），但 HUD 上「静止漂移」
「相对对齐偏转」拿 α 当**标量**用，`β→90°` 时会被 `1/cos(β)` 放大、读数乱跳，
现场人员容易误判成「设备坏了」。所以给一个直接的结论：

| β（仰角） | 判定 | 含义 |
|---|---|---|
| ≤ 80° | `ok` | α 放大 ≤ 5.76×，画面与遥测都可信 |
| 80° ~ 85° | `warn` | 遥测开始明显跳动，建议把平板放平一些 |
| ≥ 85° | `unsafe` | α 已失去意义（**画面仍正常**），遥测不可信 |

HUD 上新增一个「支架仰角」格子，装支架时实时可见；报告里给出完整判据 + 建议。

#### 判据二：`α` 有绝对参考吗

这决定「开一整天模型会不会歪」：绝对（地磁北）→ 漂移有界，展项不用管；
相对（任意起点）→ 零偏一直累积（实测约 0.1 °/min → 8 小时约 48°），必须定期归零。

做法：被动监听 `deviceorientationabsolute`（规范保证绝对），
比较 `offset = wrap(α_abs − α_dev)`。

> ⚠️ **这里我一开始想错、差点发出一个「测不出东西」的判据。**
>
> ❌ 最初的想法：看 offset 是否**恒定** —— 恒定就说明 α_dev 也是绝对的。
> ✅ 但这是错的：如果 α_dev 是**相对**的，它同样由陀螺积分得到，
> 设备偏航 θ 时 α_dev 也变 θ —— 所以 offset 只是**两个参考系的固定差**，
> 本来就是恒定的。**「offset 恒定」区分不出绝对与相对。**
>
> 真正能分辨的是 **offset 的大小**：
> - 两者都绝对 → 测同一个地磁北 → `offset ≈ 0`（只差磁偏角，中国境内约 −1° ~ −11°）
> - α_dev 是相对 → offset 取决于「任意起点」在哪 → 可以是任意值
>
> 所以 `|offset| ≥ 10°` ⇒ 可以断定 α_dev **不是**绝对参考。
> 但反过来**不成立**：`offset ≈ 0` 只是「**可能**是绝对」——
> 相对参考的任意起点也可能恰好落在北附近。**这不是证明。**
> 决定性判据是【长时间看 offset 是否持续增长】，需要跑几分钟以上。

因此页面给的是**证据 + 明确的置信度**，不是一句「是/否」：

| 判定 | 条件 | 结论 |
|---|---|---|
| `no-absolute-event` | 平台不发绝对事件（iOS 常见） | 无法用对比法取证，看静止漂移率 |
| `insufficient` | 静止样本 < 5 个 | 不下结论 |
| `insufficient-yaw` | 测试期间几乎没转向（累计 < 45°） | **不转向就无法区分参考系**，请左右转 ≥ 45° |
| `different-reference` | `offsetMaxAbs ≥ 10°` | 可断定 α_dev 非绝对，展项必须定期归零 |
| `same-reference` | `offsetMaxAbs < 10°` | 只是证据，不是证明 —— 措辞里明确写了 |

#### ★ 写这个判据时审出来的两个真 bug（都在「危险方向」）

判据写完后又把它当别人的代码审了一遍，发现两处**环绕（wrap-around）**问题。
两处都会把结论推向**宽松**的一侧 —— 也就是说，会让用户以为「不用管」，
而实际上模型会一直歪。这类错比「误报要调整」危险得多。

**Bug 1：角度取算术平均，跨 ±180° 时会抵消。**

判据量原本是「offset 的**算术平均**」。但 offset 是角度：
若真实 offset 是 180°，样本会**跨在 ±180 两侧**，例如 `{179, −179, 178, −178}`
——算术平均算出来 ≈ 0，落进 10° 阈值内 → 被误判成 `same-reference`。
**修法**：改用「偏离 0 最远的那个样本」`offMaxAbs = max|offset|`，
这就是**圆周距离**，不会因跨越而抵消。

**Bug 2：用 `max − min` 判「转过向没有」，跨 0/360° 时会假放行。**

「α 是否绝对」的判定要求设备**真的转过向**，否则样本无意义。
闸门原本用「α 的 `max − min`」估转向幅度：
α 从 358° 走到 3°（其实只转了 **5°**）→ `min=3 / max=358` → 跨度算成 **355°**
→ 被当成「转过一大圈」而放行，于是一个「其实没转向」的样本被拿来下结论。
**修法**：改用**累计路径长度** `yawTravelledDeg += |wrap180(Δα)|`（阈值也从 15° 提到 45°）。

> 这两条后来都固化成了回归用例（场景 F / G），而且**构造得比「能过」更严**：
> - 场景 F 让样本**对称地跨过 ±180**（+170…+190），使算术均值恰好落进 10° 阈值内
>   （实测 **0.25°**），而最大偏离给出 **180°** —— 只有这样才能证明「用均值判会错」，
>   否则均值法碰巧也判对，用例就白写了。
> - 场景 G 断言 `yawTravelledDeg < 45`，同时打印「朴素 max−min 会报 358°」作为对照。

#### ⚠️ 一条「写了但没牙」的检查 —— 三次负对照才找对方向

我给它加了「页面加载无 4xx/5xx」的检查，因为发现 5 个页面里有 4 个漏了空 favicon
声明、每次打开都会请求 `/favicon.ico` 拿 404。然后按惯例做负对照（抽掉一个页面的声明）：

| 版本 | 做法 | 负对照结果 |
|---|---|---|
| ① | 监听 `Network.responseReceived` 抓 4xx | ❌ **照样全绿** —— 没牙 |
| ② | 补上 `Log.entryAdded`（smoke-test 靠它抓到过这个 404） | ❌ **还是全绿** |
| ③ | 怀疑 profile 缓存，清空 `--user-data-dir` 重跑 | ❌ **依然全绿** |
| ④ | 改成**确定性 DOM 断言**：每页必须声明 `link[rel="icon"]` | ✅ **红了**（退出码 1） |

**真正的原因**：Chrome 对每个 origin 只会决定一次「要不要取 favicon」，
之后**连请求都不再发出** —— 所以任何基于网络事件 / 日志的检查都**不可能稳定观测到它**。
这类「浏览器自身行为」的回归只能用确定性 DOM 断言。

网络通道我保留了，但**改成了它真正擅长的事**：抓**走页面网络栈**的资源失败
（缺图、缺数据文件）。这一类也验证过有牙 —— 往页面塞一张 `<img src="./_nope.png">`，
检查立刻红，并且拿到了 URL：`HTTP 404 Image https://.../_nope.png`。

> **教训：一条从没红过的检查等于没写。** 写完检查必须做负对照，
> 而且**负对照要改坏产物本身，不是改断言**。
> 另外注意：我这次连续三次「换个通道再试」都是在错误方向上打转 ——
> 第三次清 profile 已经该让我意识到「问题不在通道，在这个信号本身不可观测」。

### 这条路线能做到 / 做不到

**能做到**：真实相机透视 100% 出图；真实 DEM 地形；旋转时地形稳定锁在世界里；点击选点。

**做不到**：平移跟踪。平板一旦移动位置，地形就跟着滑动 —— 这是 3DoF 的固有限制，不是 bug。
所以它适用于**「平板装在固定支架上、只转不移」**的展项形态。要支持自由移动，
需要在沙盘边框贴 AprilTag / 已知标记做绝对定位。

### 自动化回归测试

改完代码不用手动上平板验证：

```
node tools/run-all.mjs                          # ★ 一键跑全部（18 个套件）
node tools/run-all.mjs "https://127.0.0.1:8443/ar-gyro-demo.html"
```

> **默认 URL 用 HTTP 8080，不是 HTTPS 8443。** 原因是自签名证书在
> `--headless=new` + Windows 下会被拒，页面直接变成 `chrome-error://chromewebdata/`，
> 而错误页面**没有任何控制台报错** —— 于是冒烟测试照样「通过」，实际测的是空白页。
> `http://127.0.0.1` 是安全上下文（loopback），传感器和摄像头 API 完全可用，
> 不影响任何测试覆盖。真机仍然必须走 HTTPS。

`run-all.mjs` **用退出码判成败，不 grep 输出** —— 这一点有讲究：

> `reference-formula-check` 与 `vertical-stand-check` 会**故意**为被否决的候选
> 打印 ❌（负对照在工作，是好事）。我一开始用 `grep -c ❌` 统计，
> 于是把 `reference-formula-check` 里 5 个**设计内**的否定标记误报成失败，白查一遍。
> 判成败只能看退出码。为此给两个数学脚本都补上了正确的 `process.exit`。
>
> 另外那个「服务可达」探测也不能用 `fetch` —— 本项目是自签证书，
> Node 的 `fetch` 会因证书校验失败抛错，于是「13 个套件全绿」的同时
> 先打印一句「服务不可达」，把人往错方向带。改用 `https.request` +
> `rejectUnauthorized: false`。

> ⚠️ **传给浏览器套件的 URL 带了一个 `?cb=<时间戳>` 查询串，不要去掉。**
> 每个套件用的是**持久化**的临时 profile，Chrome 会把上一次的页面缓存下来。
> 实测后果是「页面明明改好了，测试却读到上一版的参数」，而且**没有任何报错** ——
> 现象是 `__gyro` 在、但新加的导出全是 `undefined`，排查方向会被带偏到
> 「导出写错了」，实际是缓存。查询串不影响任何套件：
> `hub-nav-test` 的 `baseOf()` 只取到最后一个 `/` 为止。

**漂移算法回归测试**（不需要真机，用合成陀螺仪事件）：

它注入一条时间线：前 6 秒 alpha 以 `0.1 °/min` 缓慢变化（模拟真漂移），

另外还跑两个场景：**低功耗门控**（1.2 秒间隔，复现真机问题）和**姿态平滑**。

9 项判定，实测输出：

[PASS] 转动样本 ≈ 4.2 s                       (movingMs=4209.3)
[PASS] 静止漂移量 ≈ 0.01°                     (stillDriftDeg=0.0098)
[PASS] 静止漂移率 ≈ 0.1 °/min                 (staticDriftPerMin=0.10001)  ← 精确命中
[PASS] 转动【没有】被算进漂移                  (偏转 125.9° 却没进漂移样本)
[PASS] 旧算法会严重虚高（反面对照）             (旧口径=739.5 °/min)
[PASS] 低功耗间隔也能累计样本（不再被丢弃）      (stillMs +19295（期望 ≈20000）· 丢弃 +0)
[PASS] 低功耗下漂移量估算仍准确                 (+0.0322° 期望 ≈0.0333°)
[PASS] 姿态平滑在生效（不是瞬间到位）            (变化 89.1°)
```

第 6 项是**反面对照** —— 同一段数据，旧口径会报 `739.5 °/min`，正好证明旧指标有多荒谬。
第 7、8 项直接复现了真机的低功耗场景（124 秒只有 102 个事件），
用来锁住「样本被大量丢弃」这个曾经发生过的 bug。

node tools/vertical-stand-check.mjs             # 支架仰角 / 万向锁体检（纯数学，< 1 秒）
node tools/landscape-map-test.mjs "https://127.0.0.1:8443/ar-gyro-demo.html"
```

用 CDP 的 `Emulation.setDeviceMetricsOverride` + `screenOrientation` 覆盖
`o = 0 / 90 / 180 / 270`，对 **7 种常规姿态 + 3 种欧拉角奇点姿态**共 40 个采样，7 项判定：

```
[PASS] 所有 (姿态 × 屏幕角) 下，页面姿态与 W3C 参照只差一个固定旋转   (最大偏差 0.0000°（40 个采样）)
[PASS] 该固定旋转 ≈ 单位四元数（页面与规范公式逐分量一致，含屏幕补偿 q0）(K 与单位四元数夹角 0.0000°)
[PASS] 页面确实读到了被覆盖的屏幕角（防止测试空转）                    (o=0→0° / 90→90° / 180→180° / 270→270°)
[PASS] 负对照：忽略屏幕补偿 q0 会让 K 漂起来（判据确实抓得住漏补）      (漏补 q0 时最大偏差 180.000°)
[PASS] 横屏下物理不变量成立：平板在平面内转 φ、系统把 o 改 φ → 相机逐位不变 (最大偏差 0.0000°（28 组）)
[PASS] 屏幕方向变化（设备不动）时不重锚 alignQuat —— 相机仍等于规范公式结果 (alignQuat 变化 0.0000°，相机偏差 0.0092°)
[PASS] 欧拉角奇点姿态（β=90° / 100° / −85°）下页面仍与规范公式逐分量一致 (最大偏差 0.0000°（12 个采样）)
```

> 奇点姿态那一组（β=90° / 100° / −85°）**只参与「与规范公式比对」，不参与物理不变量测试**。
> 原因：物理不变量要用**反解**构造输入，而反解在 β=±90° 本身丢信息（`0/0`）——
> 让它参与，测的是测试自己的奇点，不是页面的。

而 `reference-formula-check.mjs`（纯数学，不起浏览器）除了确认参照公式形态，
还会打印 **α / β / γ 各对应哪根世界轴** —— 用来防止「凭直觉判断欧拉角轴归属」这类误诊
（我自己就判错过一次，见上文）。

`vertical-stand-check.mjs`（纯数学）回答「平板装支架必然有仰角，会不会踩到万向锁」，
四问四答见上文「支架仰角」一节。它的结论是：**画面在任意 β 下都对，
只有 HUD 上的 α 派生读数会在 β→90° 时被 `1/cos(β)` 放大**。

这个测试的设计有三层保险，缺一层都会得出假结论：

| 保险 | 作用 |
|---|---|
| **独立参照物**（W3C 规范公式，不复用页面代码） | 否则只是拿页面验证页面 |
| **负对照**（故意漏掉 `q0`） | 证明判据抓得住「该抓的错误」，而不是恒真 |
| **防空转**（断言页面真读到了被覆盖的屏幕角） | 否则 CDP 覆盖没生效时测试会「全绿」通过 |

**展项健壮性**（连续开一整天才会暴露的三件事）：

```
node tools/kiosk-robustness-test.mjs "https://127.0.0.1:8443/ar-gyro-demo.html"
```

10 项判定，覆盖常亮锁（含「切回前台重申请」这条最容易漏的）、
显卡上下文丢失与恢复、未捕获错误留痕。详见上文「无人值守展项」一节。

## 七、连不上时的排查顺序

1. **同一网段？** 平板必须和电脑在同一个 Wi-Fi。手机热点 / 访客网络不行。
2. **路由器开了 AP 隔离？** 部分小米路由的「访客 Wi-Fi」默认隔离客户端，换主 Wi-Fi。
3. **防火墙？** 本机当前生效配置文件为「公用」，已存在 `python.exe` 的入站 TCP 放行规则
   （路径 `...\binaries\python\versions\3.13.12\python.exe`）。
   **所以务必用 `start-lan.bat` 启动**，它指向的正是这个被放行的解释器。
   若换成别的 Python 路径，需要管理员执行：
   ```
   netsh advfirewall firewall add rule name="LAN 8443" dir=in action=allow protocol=TCP localport=8443
   ```
4. **代理干扰？** 本机装有 Mihomo（虚拟网卡 `198.18.0.1`）。若异常，可临时退出代理再试。
5. **端口占用？** 换 `--port 8444` 重开。

五个页面都通过同一个 HTTPS 服务提供：

- 自检页 `https://<ip>:8443/`
- AR 测试页 `https://<ip>:8443/ar.html`
- AR 最小可复现测试 `https://<ip>:8443/ar-min.html`
- 相机 + 陀螺仪叠加 `https://<ip>:8443/ar-camera.html`
- **湖南地形 AR 沙盘 Demo `https://<ip>:8443/ar-gyro-demo.html`**

> 换网络后本机 IP 会变，证书 SAN 也要跟着变。
> 此时删除 `cert.pem` / `key.pem` 再启动，脚本会按新 IP 重新签发。
