一、问题重新定义：这不是通用 AR

通用 AR（ARKit/ARCore 的 world tracking）要解决的是"在一个未知空间里边走边建图并保持内容不漂"。而你的场景有三个强约束，把难度大幅拉低：

刚体
沙盘静止、刚性、尺寸已知，不是"未知环境"
已知几何
DEM 就在手上，虚拟地形与实体沙盘一一对应
固定展位
观察范围有限（Pad 在台面边缘 4–9 m），不需要大范围建图

所以真正要解的只有一个问题：每一帧，求相机相对沙盘坐标系的六自由度位姿 TWC。求出来之后，其余全部复用现有渲染代码。

但有一个必须先解决的物理前提：几何一致性。 现有虚拟沙盘是 4.8 × 5.5 m 台面、最大起伏 29 cm，对应真实 549.5 × 628.0 km 范围、2076 m 高差，即垂直夸张 16.0 倍（水平约 1:114,300，垂直约 1:7,159）。
实体沙盘必须按同一比例制作，否则虚拟内容与实体永远对不上。若实体已经做好了别的比例，就必须反向修改 app.js 里的 0.29 / 2076 映射常量去适配实体——这一步必须在开工前定死。

为什么推荐 A 起步

  • 不锁平台。WebXR 的 immersive-ar 在 iOS Safari 上完全不支持；而标记跟踪只需要摄像头权限——现有 camera-preview.js 已经把 getUserMedia 跑通了。这一条就排除了路线 B 的 Web 版本。
  • 精度可控且可解释。标记的沙盘坐标是"量出来的"，误差来源清晰；VIO 的漂移是"猜出来的"，不可控。
  • 改动是增量的。渲染层、地点数据、卡片布局逻辑几乎不动，只替换"相机从哪来"。
  • 能提前暴露真实问题。垂直夸张、内参、延迟、遮挡这些坑，在 PoC 阶段就会撞到，不会等到现场。
决策点：如果 PoC 后配准精度达不到 ≤10 mm，或标记遮挡过于频繁，再迁移到路线 B（Unity + AR Foundation）——此时你已经积累的标定数据、标记位姿、验收用例全部可以复用，不是白做。

三、推荐架构总览

摄像头帧
getUserMedia→ 标记检测
AprilTag · WASM→ PnP 解算
2D-3D → TWC→ 滤波融合
One Euro + IMU→ Three.js 相机→ 渲染 + DOM 卡片

关键设计原则：跟踪与渲染彻底解耦。跟踪器只吐出一个位姿对象（位置向量 + 四元数 + 时间戳 + 置信度），渲染层完全不关心它是从标记、IMU 还是编码器来的。这样将来换路线 B 时，只需要替换跟踪器实现。

// 跟踪器统一接口（新增 tracker.js）
{
  pose:      { position: Vector3, quaternion: Quaternion },  // 相机在沙盘坐标系中的位姿
  timestamp: number,        // 采集时刻（不是解算时刻）
  confidence: 0..1,         // 0 = 完全丢失
  source: 'marker' | 'imu-extrapolated' | 'frozen'
}

四、坐标系与标定（核心）

这一节是整个方案的成败所在。三个坐标系必须定义清楚：

坐标系定义来源
W — 沙盘系 原点在台面几何中心，+X 向东、+Y 向上、+Z 向南，单位米 与现有代码完全一致：(uv.x-0.5)*4.8、(0.5-uv.y)*5.5。不需要改
C — 相机系 OpenCV 约定：+X 右、+Y 下、+Z 向前（与 Three.js 的 +Z 向后差一个翻转） 解算结果
Mi — 标记系 第 i 个标记的局部坐标系，其原点/朝向在 W 中的位姿 预先测定并固化 markers.json

4.1 相机内参标定（必须先做，且与分辨率绑定）

现有代码用 BASE_VERTICAL_FOV = 48 和 zoom 模拟镜头——这是假的内参。真实 AR 必须用实际内参，否则解算出来的位姿会有系统性偏差。

参数获取方式注意
fx, fy, cx, cy离线棋盘格标定（OpenCV calibrateCamera）必须按实际采集分辨率存。若浏览器给的是 1280×720，就标定并存储该分辨率下的内参，运行时不要缩放
畸变 k1,k2,p1,p2,k3同上手机广角畸变不可忽略，尤其边缘区域；检测到角点后先 undistortPoints 再 PnP
分辨率浏览器 getUserMedia 请求值与实际值可能不同必须读 track.getSettings() 拿真实值，并据此选内参配置
坑：浏览器拿不到可靠内参。 Web 没有标准 API 暴露焦距。可行做法：① 用目标设备离线标定一次，把结果存成 JSON 随应用发布；② 或从照片 EXIF 读 35mm 等效焦距再换算。切换设备或分辨率时必须重新标定——这是运维成本，要写进 SOP。

4.2 标记布置与位姿测定

  • 标记族：用 AprilTag 36h11（比 ArUco 抗遮挡、抗模糊，误检率低）。
  • 尺寸：沙盘 4.8×5.5 m、观察距离 4–9 m，建议标记边长 120–150 mm。太小在 9 m 外像素不足；太大容易被 Pad 边框或视角切掉。
  • 数量与布局：≥6 个，沿底座四周均匀分布（每条边 1–2 个）。目标是任意合法视角下至少 3 个可见——这是解算稳定性的底线。
  • 高度：贴在底座侧立面（而非台面），因为台面起伏会遮挡；侧立面朝向观察者，且不与地形争视觉。
  • 材质：哑光覆膜，避免环境光镜面反射导致检测失败。

标记位姿测定方法（三选一，精度递增）：

  1. 图纸法：制作底座时按 CAD 图纸预留标记位置，直接读图纸坐标。误差约 ±1–2 mm。
  2. 全站仪/激光跟踪仪：现场实测每个标记四角。误差 <0.5 mm。推荐用于正式展项。
  3. 自标定法：把已知尺寸的标定板放在台面若干位置，用同一相机多视角拍摄，联合优化标记位姿与相机内参（bundle adjustment）。无需外部仪器，但实现复杂。
务必记住：markers.json 是唯一真值来源。标记一旦被碰动，整个配准就废了。物理上要做防撞保护 + 定期复核（现场 SOP：每周用标记复核工装检查一次）。

4.3 单帧解算：从标记到 TWC

1. 灰度化 + 自适应阈值 → 检测四边形候选 → 解码 ID
2. 对每个成功解码的标记 i：
     imagePoints  = 该标记 4 个角点的像素坐标（先去畸变）
     objectPoints = markers.json 中该标记 4 角点在 W 下的三维坐标
3. solvePnP(objectPoints, imagePoints, K, dist, flags=SOLVEPNP_IPPE_SQUARE)
     → 得到 R, t（相机在标记系中的位姿）
4. 若可见标记 ≥ 2：对各自解算结果做一致性检查
     - 重投影误差 RMS 应 < 1.5 px，超阈值的标记剔除
     - 用所有内点联合求解（多标记共面或非共面都可）
5. 得到 T_WC（相机在沙盘系中的位姿）
6. 转换到 Three.js 约定（Y 轴向上、右手系、相机朝 -Z）：
     threeCamera.position.copy(T_WC.position)
     threeCamera.quaternion.copy(T_WC.quaternion)

实现建议：solvePnP 用 IPPE_SQUARE（单标记四角专用，比通用 EPnP 更稳）；多标记用 RANSAC 剔除误检。整个流程可以走 OpenCV.js（WASM），但更推荐用 apriltag 的 WASM 编译版做检测、自己写 PnP——OpenCV.js 体积大（~8 MB）。

六、稳定性：滤波与丢失恢复

AR-INTEGRATION.md 里已经列了正确方向，这里是可落地的参数化实现。

6.1 滤波：位置与姿态分开处理

量方法建议参数
位置One Euro Filter（自适应低通，慢速时强平滑、快速时低延迟）minCutoff = 0.8 Hz、beta = 0.007、dCutoff = 1.0
姿态四元数 slerp 向目标姿态插值（不要对欧拉角滤波，会有万向锁与跳变）平滑系数按帧率归一：α = 1 - exp(-dt/τ)，τ ≈ 0.04 s
静止死区位姿变化小于阈值时冻结输出，消除亚像素抖动角度 < 0.05°、位置 < 0.5 mm 时不动
绝对不要做的事：对地形、图标、连线、卡片分别滤波。这会让它们以不同相位漂移，出现"卡片和连线脱开"的经典 bug。正确做法是只对唯一的 TWC 滤波，所有内容共享同一变换——现有代码已经天然满足这一点（全部挂在同一个 scene 下）。

6.2 丢失恢复策略

状态条件行为
正常可见标记 ≥ 3，重投影 RMS < 1.5 px正常解算 + 滤波
降级可见标记 1–2仍解算但提高平滑强度；同时用 IMU 陀螺仪积分补旋转
短时丢失< 200 ms 无解冻结最后可靠位姿，画面保持（用户几乎察觉不到）
持续丢失> 200 ms内容整体淡出至 30% 不透明度，界面提示"请将 Pad 对准沙盘"，不要继续显示过期锚点
重新锁定再次解算成功淡入恢复；若位姿跳变 > 50 mm，做 0.3 s 过渡而不是瞬移

IMU 补充：DeviceOrientationEvent 在 iOS 需要用户手势授权（requestPermission()），且浏览器给的姿态精度有限、没有磁偏补偿。它只适合做短时（<1 s）旋转外推，不能作为独立跟踪源。

七、遮挡：用已知 DEM 做深度遮挡

这是本项目相对通用 AR 的最大优势——你手里有精确的三维几何，不需要深度传感器。

核心洞察：配准成功后，虚拟 DEM 网格与实体沙盘表面在空间上重合。所以只要让虚拟地形继续写入深度缓冲但不写颜色，它就是一个完美的遮挡体——山体后面的扫描点会被自动正确遮挡。 
// 修改 app.js 的 onReferenceChange 回调
onReferenceChange(visible) {
  if (arMode) {
    // AR 模式：地形不显示，但保留深度写入，充当遮挡体
    terrain.visible = true;
    terrain.material.colorWrite = false;   // 关键
    terrain.material.depthWrite = true;
    for (const o of referenceObjects) o.visible = false;  // 底座/地面网格隐藏
  } else {
    terrain.visible = visible;
    terrain.material.colorWrite = true;
    for (const o of referenceObjects) o.visible = visible;
  }
}

现有代码已经满足前提条件：点云与连线是 transparent: true, depthWrite: false, depthTest: true，会被排在不透明物体之后渲染，因此能正确接受地形的深度测试。只需上面这一处改动。

进阶：真实遮挡（可选）

  • LiDAR 方案：若 Pad 是 iPad Pro / iPhone Pro，ARKit 的 sceneDepth 可提供真实深度图，能遮挡"实体沙盘上放的其他物体"（如人手的投影、边缘挡板）。代价是必须走原生路线 B。
  • 模型误差补偿：实体沙盘的制作精度（±1–2 mm）会造成局部遮挡边缘不齐。可对遮挡体做微小的向内收缩（法线方向 -1 mm），避免出现"虚拟内容在实体表面上一闪一闪"的 z-fighting 观感。
  • 注意扫描点的抬高量：现有点云/连线统一抬高 lift = 3.5 mm。遮挡体就是原始 DEM，所以贴合表面的点不会被自己遮挡——这个设计在 AR 下依然成立，不需要改。

八、交互重设计

现有交互是"鼠标驱动"，在 AR 中大部分会被物理运动取代。需要明确哪些留、哪些改、哪些删。

现有交互AR 中的处理原因
支架滑杆：安装高度 / 离中心距离 / 沿边左右位置移除（降级为校准面板）Pad 的真实位置由物理支架决定，并由跟踪测得。手动调只会与真实位姿打架
镜头缩放 1–3.5×移除真实光学变焦由设备决定；数字变焦会破坏内参与配准
拖动画面改视线 / 方向键移除直接转动 Pad 即可，这是 AR 最自然的部分
滚轮调距离移除走近走远即可
准心 dwell 聚焦（0.5 s）保留天然适配 AR，是凝视交互的标准范式
点击地形触发扫描改为触屏点选射线从真实相机位姿发出即可，逻辑不变
侧栏地点列表保留（改为浮层）作为"看不准时"的兜底选择方式
信息卡四角展开保留已从世界坐标投影到屏幕，相机一换就自动跟随
现有架构的一个宝贵特性：updateSites() 与 layoutStory() 已经用 worldPoint.project(camera) 把三维锚点投到屏幕坐标，再用 DOM 渲染卡片。这意味着只要把真实位姿喂给 camera，整套 UI 会自动跟随，几乎不用改。这是当初设计得好的地方。

需要新增的交互

  • 校准入口：首次部署时引导操作员把 Pad 对准沙盘，确认跟踪锁定，写入 markers.json 校验值。
  • 跟踪状态指示：一个不显眼的小角标，显示"已锁定 / 降级 / 搜索中"，方便现场人员判断。
  • 触屏点选：pointerup 逻辑已有，只需把射线源从"模拟相机"换成"真实相机"，无需改动。

2

稳定性工程

One Euro 滤波（位置）+ slerp（姿态）；时间戳贯穿链路 + IMU 外推；实现五态丢失恢复状态机；加跟踪状态指示。

交付：静止抖动 ≤1 px · 运动延迟 ≤50 ms · 重定位 <800 ms

3

遮挡与视觉融合

启用 colorWrite=false 深度遮挡；对遮挡体做 1 mm 内缩避免 z-fighting；校正全息内容的亮度/对比度使其在实景上可读；可选接入 LiDAR 真实遮挡。

交付：山体后内容正确遮挡 · 实景可读性通过目视评审

4

交互重设计

移除鼠标专属交互（滑杆/拖动/滚轮），改为触屏 + 凝视；校准入口与引导流程；卡片锚定世界坐标的边界情况（贴边、遮挡、多地点重叠）。

交付：AR 交互规格 · 无鼠标可完整操作

5

现场验收与调优

按第 11 节用例逐条测试；在真实 Pad、真实观察距离、真实光照下重标所有阈值（网页像素参数不等于设备角度阈值）；输出运维 SOP。

交付：验收报告 · 现场调参表 · 运维 SOP（含标记复核流程）

决策点设在阶段 2 结束。如果滤波后仍达不到验收线，或标记遮挡率过高，此时切换到路线 B（Unity + AR Foundation）。已有的标定数据、标记位姿、验收用例、交互规格全部可复用，沉没成本很低。

十一、验收标准与测试用例

11.1 量化指标

指标目标可接受测量方法
配准精度（锚点 vs 实体地物）≤ 10 mm≤ 20 mm在沙盘上放置已知坐标的检验点，测量虚拟锚点投影偏差
静止抖动≤ 1 px≤ 2 pxPad 固定不动录屏 10 s，统计锚点像素坐标标准差
运动延迟≤ 40 ms≤ 80 ms快速转动时录屏，逐帧比对实体边缘与虚拟内容边缘
重定位时间< 500 ms< 1 s遮住摄像头再放开，计时到重新锁定
帧率60 fps30 fps长时间运行统计
遮挡正确率山体后的扫描点 100% 不可见目视 + 抽样像素比对

11.2 必测场景（现场验收清单）

  1. 小幅手抖：Pad 轻微抖动 10 s，内容不应出现可见晃动或"呼吸"。
  2. 快速转动：快速左右/上下扫视，内容不应滞后脱节或甩尾。
  3. 地点边界停留：准心在地点图标边缘反复进出，卡片不应反复开关（现有 160 ms 容错需在真实抖动下重新标定）。
  4. 遮挡识别物：用手或挡板遮住部分标记，跟踪应降级而非跳变；遮住过半标记，应进入"搜索中"提示。
  5. 重新入镜：Pad 完全移开再转回，应能自动重新锁定且无内容瞬移。
  6. 低帧率：人为降帧至 15 fps，滤波与丢失策略不应失控。
  7. 长时间运行：连续运行 2 h，检查位姿漂移与内存占用。
  8. 边缘视角：走到沙盘四角与最远/最近观察距离，配准精度应保持一致。
  9. 环境光变化：开/关室内灯、拉窗帘，跟踪不应中断。
  10. 多点位重叠：两个地点图标在屏幕上靠近时，卡片布局不应重叠错乱。

十二、风险与降级路径

风险概率影响应对 / 降级
实体沙盘几何与虚拟不一致 高 致命——配准永远对不上 阶段 0 必须锁死；若实体已做好，改 app.js 的垂直映射常量去适配，并重新生成 assets/
标记遮挡率过高 中 频繁丢失，观感差 增加标记数量与冗余布局；提高 IMU 外推权重；必要时加台面标记（做成低调的装饰边框图案）
浏览器内参不可靠 中 系统性配准偏差 逐设备离线标定并随应用发布；建立"设备-内参"对照表
WASM 检测性能不足 低 帧率下降 降分辨率 + ROI 搜索 + Web Worker 分离；仍不足则迁移原生
iOS 浏览器限制 低 摄像头/传感器权限 标记方案只需 getUserMedia，iOS 支持良好；IMU 需 requestPermission() 用户手势授权，要做好引导
现场光照导致检测失败 中 演示中断 哑光标记 + 均匀照明设计；准备备用照明方案；加"检测质量"实时指示供现场排查

降级阶梯（按代价从低到高）

  1. 标记为主 + IMU 外推（推荐基线）
  2. 标记 + 台面纹理特征点混合跟踪（提高遮挡容忍度）
  3. 机械编码器辅助：若支架是固定的，给各轴装编码器，标记只用于低频校正
  4. 迁移 Unity + AR Foundation（原生 VIO + 图像锚点 + LiDAR 遮挡）
  5. 退回"增强版固定机位"：Pad 完全固定不动，取消跟踪，只保留预标定的单一视角 + 摄像头实景合成——即当前 Demo 的强化版，至少不会失败
